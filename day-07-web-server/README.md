# Day 7 · Web Server

Web Server 这一题的价值，不在于“再造一个框架”，而在于把浏览器访问网页时那条被日常开发隐藏掉的链路亲手走一遍：连接怎么建立，请求怎么读，HTTP 怎么解析，路由怎么命中，文件怎么返回，连接什么时候关闭，服务为什么会在并发下变慢。只要这条链路真正通了，后面再看 Nginx、Node.js、Go `net/http`、Python WSGI/ASGI，理解都会扎实很多。

## build-your-own-x 对应原始项目地址
- [Web Server](https://github.com/codecrafters-io/build-your-own-x#build-your-own-web-server)

## 这是什么

这是一个“从 TCP socket 往上搭 HTTP 服务”的学习主题。它不是教你怎么调用现成框架，而是让你自己实现一个最小可工作的 Web Server，从而理解 Web 请求的真实形态。

浏览器发起一次访问，本质上发生的是下面这件事：

1. 客户端通过 TCP 连接到服务器的某个 IP:Port。
2. 服务器在监听 socket 上 `accept` 到一个新连接。
3. 客户端发送 HTTP 报文，里面有请求行、请求头、可选请求体。
4. 服务器从连接 socket 读取字节流，解析出方法、路径、协议版本、头字段和消息体。
5. 服务器决定这是静态资源请求，还是动态路由请求。
6. 服务器构造 HTTP 响应，写回状态行、响应头和响应体。
7. 连接被关闭，或者按 keep-alive 规则继续复用。

所以，Web Server 不是一个抽象名词，而是一条明确的请求-响应流水线。这个主题就是在拆开这条流水线，让你知道每一层到底做了什么。

## 怎么使用

最有效的方式不是一次性写“大而全”的服务器，而是按能力分层推进。建议把这份 README 当成实现顺序和检查清单。

1. 先写一个最小版本：监听端口，接到连接后无论请求是什么都返回固定文本。
2. 再补请求解析：至少能正确读出 `GET / HTTP/1.1` 这样的请求行，并识别请求头结束位置 `\r\n\r\n`。
3. 再补路由：让 `/`、`/hello`、`/health` 返回不同结果，建立“路径 -> 处理逻辑”的映射。
4. 再补静态资源：把某个目录映射为可访问文件，返回 HTML、CSS、图片等内容。
5. 再补动态处理：支持根据参数、路径或请求体生成响应，而不是只返回硬编码文本。
6. 最后处理现实问题：并发、超时、半开连接、错误码、日志、性能边界。

建议每完成一层，都用最直接的方式验证，而不是等全部做完再排查。

可以用 `curl` 先验证 HTTP 是否成立：

```bash
curl -i http://127.0.0.1:8080/
curl -i http://127.0.0.1:8080/hello
curl -i http://127.0.0.1:8080/missing
```

也可以直接观察一次原始请求格式：

```http
GET /hello HTTP/1.1
Host: 127.0.0.1:8080
User-Agent: curl/8.x
Accept: */*

```

一个最小但合法的响应通常长这样：

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 12

Hello World!
```

如果你已经能稳定做到“读完整请求 -> 解析路径 -> 返回合法响应”，就说明核心骨架已经立住了。后面的并发、静态文件、动态逻辑，本质上都是在这条骨架上逐步扩展。

## 核心原理

### 1. 请求-响应模型

Web Server 的中心思想很简单：客户端发请求，服务器回响应。但真正重要的是，这不是函数调用，而是跨网络传输的协议交互。

一个 HTTP 请求通常包含三部分：

1. 请求行：方法、路径、协议版本，例如 `GET /index.html HTTP/1.1`
2. 请求头：例如 `Host`、`Content-Type`、`Content-Length`、`Connection`
3. 请求体：常见于 `POST`、`PUT`、`PATCH`

一个 HTTP 响应也有三部分：

1. 状态行：例如 `HTTP/1.1 404 Not Found`
2. 响应头：例如 `Content-Type`、`Content-Length`、`Cache-Control`
3. 响应体：真正返回给客户端的内容

这里最容易踩的坑不是“不会写代码”，而是对协议边界没概念：

1. 报文头和消息体之间必须有一个空行。
2. `Content-Length` 必须与实际字节数一致。
3. 不能把“读到一次 socket 数据”误认为“已经读完一个完整请求”。
4. 不能把“返回了字符串”误认为“已经返回了合法 HTTP 响应”。

你真正理解 Web Server 的标志，不是会返回 JSON，而是知道 JSON 只是响应体；在它外面还有完整的 HTTP 协议壳。

### 2. `socket` / `listen` / `accept`

一个最小 TCP 服务器的底层流程通常是：

1. `socket`：创建一个监听 socket。
2. `bind`：把它绑定到本机地址和端口。
3. `listen`：让内核开始为这个端口排队等待连接。
4. `accept`：从等待队列里取出一个客户端连接，得到新的连接 socket。
5. `read` / `recv`：从这个连接读取请求数据。
6. `write` / `send`：把响应写回这个连接。
7. `close`：关闭连接，或者继续复用。

这里必须建立两个清晰概念：

1. 监听 socket 负责“接客”，连接 socket 负责“服务当前这个客户端”，两者不是一个东西。
2. 服务器面对的不是“一个请求”，而是一连串不断到来的连接和请求。

`listen` 的意思不是“开始处理 HTTP”，而是“这个端口现在可以被连接了”；`accept` 才是从抽象的监听状态进入具体的会话处理。很多人卡在这里，是因为脑子里没有“监听 socket”和“连接 socket”这两个对象的区分。

### 3. HTTP 报文结构与解析

从 socket 读到的是一段字节流，不自带边界，也不自带“这是一行头部”的语义。解析器必须自己做三件事：

1. 判断请求头是否读完整了，通常依赖 `\r\n\r\n`。
2. 解析第一行，拆出方法、路径、HTTP 版本。
3. 根据头字段决定是否还要继续读取请求体，例如读取 `Content-Length` 指定的字节数。

这意味着“请求对象”不是天然存在的，而是你从原始字节里组装出来的数据结构。一个入门实现通常先收窄边界：

1. 只支持 `GET` 和 `POST`
2. 只支持 `HTTP/1.1`
3. 只支持 `Content-Length`，先不处理分块传输
4. 先用短连接，暂时不实现复杂的 keep-alive 复用

这种收窄不是偷懒，而是把精力集中在最重要的问题上：你是否真的知道一个请求是如何被“读出来”和“拆出来”的。

### 4. 静态资源与动态路由

Web Server 处理请求时，至少要做一个分流判断：这次请求是去读一个现成文件，还是去执行一段应用逻辑。

静态资源处理通常对应：

1. 把 URL 路径映射到某个安全目录下的文件。
2. 根据扩展名设置 `Content-Type`，例如 HTML、CSS、JS、PNG。
3. 正确处理文件不存在、无权限、路径越界等情况。

动态路由处理通常对应：

1. 根据方法和路径匹配处理函数，例如 `GET /users`、`POST /login`。
2. 从路径参数、查询参数、请求头、请求体中提取业务输入。
3. 生成运行时响应，而不是读取磁盘上的固定文件。

这两类能力最好分开理解。静态资源偏“文件系统映射”，动态路由偏“请求分发器”。真实框架会把这两件事都包装起来，但手写服务器时，你会清楚看到它们是两套不同的问题。

还要特别注意一个安全边界：路径不能直接拿来拼接文件路径，否则很容易出现目录穿越，例如请求 `../../etc/passwd`。所以静态资源服务不是“把文件吐出去”，而是“在安全目录内按协议返回文件”。

### 5. 并发与连接管理

单连接版本适合学习，但现实中的 Web Server 一定会遇到并发：多个客户端同时连进来，有的请求快，有的请求慢，有的客户端甚至会连上后迟迟不发完整数据。

这会立刻带来连接管理问题：

1. 一个请求阻塞时，其他请求能不能继续处理。
2. 每个连接占用多少线程、内存和文件描述符。
3. 慢客户端会不会把服务拖死。
4. 连接是否复用，什么时候超时关闭。

常见模型包括：

1. 串行模型：最简单，但一个慢请求会堵住所有后续请求。
2. 每连接一个线程：直观，但连接多了线程成本很高。
3. 线程池：用固定工作线程处理请求，更容易控制资源上限。
4. 事件驱动：用 `select`、`poll`、`epoll` 等机制管理大量连接，吞吐更高，但实现复杂度明显上升。

学习时最重要的不是记住名词，而是建立直觉：Web Server 的性能瓶颈常常不是“算得慢”，而是“等 I/O 的时候如何不把整个系统卡住”。并发模型本质上是在解决“等待期间 CPU 和线程怎么安排”。

### 6. 错误处理与性能边界

真正能区分“能跑”和“可用”的，不是成功路径，而是失败路径。

一个最小可用的 Web Server 至少要覆盖这些错误：

1. 请求行格式错误，返回 `400 Bad Request`
2. 路径不存在，返回 `404 Not Found`
3. 方法不允许，返回 `405 Method Not Allowed`
4. 请求太大或超时，返回合适的错误并主动断开连接
5. 服务器内部异常，返回 `500 Internal Server Error`

同时要认识到它的性能边界通常也很明确：

1. 大文件返回会暴露内存拷贝和阻塞写问题。
2. keep-alive 会提升连接复用效率，但也会增加连接生命周期管理复杂度。
3. 大量短连接会放大 `accept`、上下文切换和队列积压成本。
4. 恶意或异常客户端会暴露超时、限流、最大头部大小、最大请求体大小等机制是否存在。

所以，Web Server 的后半段学习重点，不只是“功能支持更多”，而是“系统在压力和错误下怎么不失控”。

### 7. 一次请求的完整链路

可以用下面这条线把所有概念串起来：

`客户端建连 -> 服务器 listen -> accept 新连接 -> 读取 socket 字节流 -> 解析 HTTP 报文 -> 判断静态资源或动态路由 -> 构造状态行/响应头/响应体 -> 写回响应 -> 关闭或复用连接`

如果你能把这条链路在脑中完整复述出来，并且知道每一步可能失败在哪里，说明你对 Web Server 已经不只是“知道名词”，而是开始具备系统级理解了。

## 适用场景

这个主题特别适合下面几类目标：

1. 想补齐网络编程、HTTP、I/O 模型这些底层认知的人。
2. 已经会写 Web API，但对框架底层请求处理过程没有把握的人。
3. 准备系统设计、后端基础、网络协议类面试的人。
4. 需要做教学演示、协议实验、极简内网工具或嵌入式控制台的人。

如果目标是“建立第一性理解”，它非常合适，因为它会把操作系统、网络协议、文件系统和应用层分发逻辑放在同一个问题里统一观察。

## 不适用边界

自己从零实现的学习型 Web Server，通常不适合直接承担生产级公网服务，尤其在以下方面会很快碰到边界：

1. TLS/HTTPS、证书轮换、SNI、现代浏览器兼容性
2. HTTP/2、HTTP/3、多路复用、压缩、流控
3. 高性能大文件传输、零拷贝、缓存协商、范围请求
4. 完整的反向代理、负载均衡、限流、熔断、健康检查
5. 安全防护，例如慢请求攻击、请求走私、头注入、目录穿越
6. 完整可观测性，包括结构化日志、指标、追踪和报警

它的主要用途是“学习系统如何成立”，不是替代成熟的 Nginx、Caddy、Apache，或者语言生态里已经高度打磨过的应用服务器。

## 为什么它重要

Web 开发里很多看似理所当然的抽象，其实都建立在这个主题上：

1. 路由、中间件、控制器、请求对象、响应对象，本质上都是对请求-响应链路的包装。
2. `404`、超时、连接重置、静态资源失败、端口占用这些日常问题，只有理解底层链路后才容易快速定位。
3. 并发、阻塞、backlog、keep-alive、线程池、事件循环这些概念，一旦脱离 Web Server 的上下文，很容易只背名词不懂因果。
4. 你会更清楚框架帮你解决了什么，也更清楚它在哪些地方隐藏了复杂度和成本。

这就是它重要的地方：不是为了人人都去手写服务器，而是为了建立对 Web 系统的因果感。没有这层因果感，很多“会用”最终都会停留在表面。

## 建议延伸

如果基础版本已经打通，后续最值得补的不是花哨功能，而是那些会显著提升理解密度的扩展：

1. 支持 `POST`、表单、JSON，请求体解析从固定长度走向更完整的协议处理。
2. 支持 keep-alive，观察连接复用如何改变请求处理流程。
3. 为静态资源增加 MIME 映射、缓存头、目录索引和安全校验。
4. 从串行模型升级到线程池或事件循环，比较吞吐量、延迟和实现复杂度。
5. 增加超时、最大请求头大小、最大请求体大小，理解服务端保护机制。
6. 增加访问日志和错误日志，建立“请求发生过什么”的可观测性。
7. 对比成熟实现，例如 Nginx、Caddy、Node.js `http`、Go `net/http`，看它们分别把复杂性藏在了哪里。

延伸时可以始终追问两件事：

1. 我现在用到的抽象，底层具体对应哪一步 socket / HTTP / I/O 处理？
2. 如果连接变多、请求变慢、输入变坏，这个设计会先从哪里出问题？

这两个问题能越答越具体，说明你对 Web Server 的理解就在持续变深。
