# Day 3 · Text Editor

## build-your-own-x 对应原始项目地址

- [Text Editor](https://github.com/codecrafters-io/build-your-own-x#build-your-own-text-editor)

## 这是什么

Text Editor（文本编辑器）是最基础、也最容易被低估的软件系统之一。它表面上只是“输入、删除、保存文字”，本质上却是在做一件很难的事：**把人类连续、模糊、频繁的编辑意图，稳定映射成对文本缓冲区的精确操作**。

从 build-your-own-x 的视角看，自己实现一个文本编辑器，不是为了重复造一个记事本，而是为了理解：光标为什么能移动、文本为什么能高效插入删除、屏幕为什么能实时刷新、文件为什么能被正确保存。

## 怎么使用

一个最小文本编辑器通常支持这样的工作流：

1. 打开文件并载入内容。
2. 用键盘移动光标。
3. 在光标位置插入或删除字符。
4. 对多行文本进行滚动显示。
5. 把内存中的内容写回磁盘。

在更成熟的编辑器里，还会继续叠加：

- 查找与替换
- 语法高亮
- 撤销与重做
- 多缓冲区/多标签页
- 自动缩进
- 插件机制

所以“怎么使用”很简单，但“为什么它用起来顺滑”背后却是一整套数据结构与渲染机制在配合。

## 核心原理

### 1. 文本缓冲区：编辑器真正操作的不是文件，而是内存状态

文件只是持久化结果。编辑器打开文件后，通常会先把内容载入到内存里的某种缓冲结构，再对这份结构做修改。

关键问题在于：

- 如果文本存在普通字符串里，频繁插入删除会很慢。
- 如果文本很大，整段复制会导致性能下降。

因此，编辑器常见的数据结构包括：

- **Array of Lines**：实现简单，适合教学与最小编辑器。
- **Gap Buffer**：在光标附近预留空隙，局部编辑很高效。
- **Rope**：把大文本拆成树状片段，适合超大文件。
- **Piece Table**：原始内容与新增内容分离，适合撤销/重做和复杂编辑历史。

编辑器的手感，很多时候首先取决于缓冲区设计。

### 2. 光标系统：你看到的是位置，系统维护的是坐标映射

用户以为自己在“第几行第几列”编辑，但程序内部通常要同时处理：

- 文本中的逻辑位置
- 屏幕上的显示位置
- 滚动后的相对位置
- Tab、宽字符、换行带来的偏移差异

这意味着光标移动不是简单的 `x + 1`、`y + 1`。真正难点是：**逻辑文本坐标如何映射到终端或窗口坐标**。

### 3. 屏幕渲染：不是整屏重画越多越好，而是尽量只更新必要部分

最小编辑器常用“整屏刷新”策略：每次按键后重新绘制全部内容。这样实现简单，但规模一大就会卡顿。

更高阶的编辑器会做：

- dirty region 局部更新
- 状态缓存
- 光标与文本分层绘制
- 高亮与布局分阶段处理

因此，文本编辑器其实也是一个轻量级实时渲染系统。

### 4. 输入处理：按键不是字符，编辑器先处理事件语义

用户按下键盘时，编辑器接收到的并不总是直接字符，还可能是：

- 方向键
- Ctrl / Alt 组合键
- 删除键、回车键
- ESC 序列
- 输入法相关事件

所以编辑器常常先做“按键解码”，再转换为编辑命令，如：

- move-left
- insert-char
- delete-backward
- save-file

也就是说，编辑器内部首先是**事件驱动状态机**，然后才是字符写入。

### 5. 保存机制：文件写入不是“顺手存一下”，而是状态一致性问题

保存时至少要考虑：

- 内存内容如何序列化为文件
- 是否覆盖原文件还是写临时文件再替换
- 异常中断时如何避免文件损坏
- 换行符、编码、权限如何处理

一个“可靠的保存”看似简单，实际上涉及最基本的数据安全意识。

## 适用场景

- 代码编辑器与 IDE 的基础理解
- 终端编辑器实现练习
- 学习数据结构如何影响交互性能
- 学习事件循环、渲染刷新、文件 I/O
- 理解更复杂软件（IDE、文档协作工具）的底层雏形

## 不适用边界

- 只想快速完成业务功能，而不关心底层交互原理
- 需要富文本排版、图文混排、复杂版式时，纯文本编辑器模型不够
- 需要多人实时协作时，仅靠本地编辑器架构不足以解决冲突合并
- 需要完整 IDE 能力时，最小编辑器教程只覆盖很小一部分

## 为什么重要

文本编辑器是一个非常典型的“看起来简单、做起来系统性很强”的项目。

它重要，不只是因为程序员每天都在使用编辑器，而是因为它浓缩了很多软件工程核心问题：

1. **数据结构决定交互体验**：插入删除是否顺滑，不是 UI 细节，而是底层表示法决定的。
2. **事件驱动如何管理状态**：每次按键都会改变内部状态与外部显示。
3. **显示层与数据层如何解耦**：文本内容、光标位置、滚动窗口、语法高亮并不是一回事。
4. **持久化如何保证可靠**：保存文件时，任何粗糙实现都可能带来数据损坏。

如果说命令行工具教你“把能力做成接口”，shell 教你“把工具连接起来”，那么文本编辑器教你的是：**如何把持续交互中的复杂状态管理好。**

## 建议延伸

- 先实现一个终端版最小编辑器：支持打开、移动、插入、删除、保存。
- 对比 `kilo`、`vim`、`nano` 一类教程，观察它们怎样处理终端输入与屏幕刷新。
- 继续研究 Gap Buffer、Piece Table、Rope 三种结构，理解它们为何会影响编辑手感。
- 延伸到语法高亮、撤销/重做、LSP 支持，理解现代代码编辑器为何会变成一个复杂平台。
