# Database

## 这是什么

数据库（Database）是一套**有组织地存储、读取、更新和管理数据**的方法与系统。你可以把它理解成“比文件更可靠、比内存更持久、比手工整理更可控”的数据基础设施。

如果只看本质，数据库解决的是三件事：

1. 数据放在哪里，断电后还能在。
2. 数据怎么快速找到，而不是一条条翻。
3. 多个人、多程序同时读写时，如何尽量不乱、不丢、不冲突。

它不是单纯的“数据仓库”，而是**数据的存储规则 + 查询能力 + 一致性控制 + 性能优化**的组合。

## 怎么使用

最常见的使用方式可以概括为四步：

1. 先定义要存什么数据，比如用户、订单、文章、日志。
2. 再设计结构，比如表、字段、主键、索引，或者文档结构、键值结构。
3. 通过程序执行增删改查，也就是写入、读取、更新、删除。
4. 随着数据变多，继续处理索引、事务、备份、权限、扩容这些问题。

一个典型流程是：

- 应用程序发出查询请求。
- 数据库解析请求，决定怎么执行。
- 它从磁盘或内存中找到目标数据。
- 如果发生写入，还要保证写入顺序、并发安全和持久化。
- 最后把结果返回给应用。

所以从使用者视角看，数据库像一个“会理解数据结构、会帮你查找、还能尽量保证不出错”的后端服务。

## 核心原理

理解数据库，抓住下面几个核心点就够了。

**1. 持久化**

内存快，但会丢；磁盘慢，但能长期保存。数据库的第一原则，就是把重要数据可靠地落到持久介质中。很多数据库会先写日志，再写正式数据，以降低故障时的数据丢失风险。

**2. 数据模型**

数据库不是把所有内容乱塞进去，而是先规定“数据长什么样”。

- 关系型数据库：用表、行、列来组织数据。
- 文档数据库：按 JSON 一类的文档组织。
- 键值数据库：用 key 对应 value。
- 图数据库：用点和边描述关系。

数据模型决定了你怎么表达业务，也决定了查询和扩展方式。

**3. 查询与执行**

用户写的是“我要什么”，数据库还要进一步决定“怎么拿”。这中间通常会经历：

- 解析查询语句
- 生成执行计划
- 选择是否走索引
- 决定扫描、过滤、连接、排序的顺序

所以数据库性能好不好，不只是“机器快不快”，更取决于**执行路径是不是合理**。

**4. 索引**

索引像书的目录。没有索引时，数据库可能要全表扫描；有索引时，可以更快定位目标数据。

但索引不是越多越好，因为：

- 写入时要维护索引，成本会上升
- 索引本身占空间
- 设计不合理时，可能依然查不快

索引本质上是在“读性能”和“写成本”之间做交换。

**5. 事务与一致性**

数据库经常要处理“操作做一半失败”的情况，比如转账时，扣款成功但加款失败。事务就是把一组操作看成一个整体：要么都成功，要么都回滚。

这背后涉及 ACID：

- Atomicity：原子性，不做一半
- Consistency：一致性，结果不违背规则
- Isolation：隔离性，并发时尽量互不干扰
- Durability：持久性，提交后尽量不丢

事务让数据库从“能存数据”升级为“能安全处理业务状态变化”。

**6. 并发控制**

多个请求同时改数据时，数据库需要避免脏读、丢失更新、互相覆盖等问题。常见方法包括锁、MVCC（多版本并发控制）等。它们的目标不是让并发消失，而是在正确性和吞吐量之间找到平衡。

## 适用场景

数据库适合这些场景：

- 需要长期保存数据，而不是进程结束就丢失。
- 需要按条件查询、筛选、排序、聚合数据。
- 多个用户或服务要共享同一批数据。
- 业务对一致性有要求，比如账户、库存、订单、权限。
- 数据规模会增长，不能长期依赖文本文件或内存结构硬撑。
- 需要备份、恢复、权限控制、审计等工程能力。

一句话概括：**只要数据开始成为系统核心资产，数据库通常就该上场。**

## 不适用边界

数据库很重要，但不是所有问题都该先上数据库。

这些情况未必适合：

- 只是一次性的小脚本，数据量很小，用本地文件就够。
- 只是临时缓存，丢了也没关系，更适合内存缓存系统。
- 读写模型极其简单，没有共享需求，数据库反而增加复杂度。
- 追求极低延迟的特定场景，可能需要专门的内存系统或定制存储结构。
- 数据结构极不稳定、探索性很强，先用轻量方案验证可能更划算。

边界判断的关键不是“数据库好不好”，而是：**它带来的可靠性和管理能力，是否值得你支付额外复杂度。**

## 为什么重要

数据库重要，不只是因为它“能存数据”，而是因为现代软件几乎都围绕数据运行。

- 没有数据库，很多系统只能停留在“能跑一次”的阶段。
- 有了数据库，系统才能支持用户历史、状态保存、跨设备同步、统计分析和业务协作。
- 数据库把“程序逻辑”与“数据生命周期”分开，让系统更可维护。
- 它也是很多更高层能力的基础，比如搜索、推荐、报表、风控、审计和机器学习数据管道。

从工程视角看，数据库是应用系统的“长期记忆”和“状态中心”。

## 建议延伸

如果已经理解“数据库是解决持久化、查询、并发和一致性的系统”，下一步建议按这个顺序继续深入：

1. 先学关系型数据库的基本概念：表、主键、外键、索引、事务。
2. 再理解 SQL 查询为什么有时快、有时慢，重点看执行计划和索引命中。
3. 接着学习数据库内部结构，比如 B+ 树、WAL、页、缓冲池、MVCC。
4. 然后再看不同类型数据库的取舍：关系型、键值、文档、列式、图数据库。
5. 最后再进入分布式主题，比如复制、分片、一致性、故障恢复。

如果只能记住一句话，那就是：

**数据库不是“存东西的地方”，而是“在规模增长和多人协作下，仍然能把数据管理正确、查找高效、状态可控”的系统。**
