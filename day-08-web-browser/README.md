# Day 08 · Web Browser

这份 README 不是教你“做一个能替代 Chrome 的浏览器”，而是帮助你通过一个可控、可实现的 toy browser，理解浏览器最核心的内部机制：网页为什么能从一段文本，变成屏幕上的排版、颜色、交互和动态效果。

## 1) build-your-own-x 对应原始项目地址

`build-your-own-x` 中 Web Browser 的精确入口是：

- [Build your own Web Browser](https://github.com/codecrafters-io/build-your-own-x#build-your-own-web-browser)

这个条目下面当前列出两条原始学习项目：

- Rust: [Let's build a browser engine](https://limpet.net/mbrubeck/2014/08/08/toy-layout-engine-1.html)
- Python: [Browser Engineering](https://browser.engineering/)

两者的侧重点不完全一样：

- `Let's build a browser engine` 更像“从渲染引擎最小闭环切进去”，重点是 DOM、CSS、布局、绘制，适合先抓住浏览器最核心的数据流。
- `Browser Engineering` 覆盖更完整，从 URL 和 HTTP 请求开始，一直走到 HTML 解析、CSS、事件、表单、JavaScript、安全、线程与合成，适合系统性学习。

如果你的目标是“理解浏览器为什么这样工作”，这两条路线最好结合着看：前者帮助你快速建立脑内模型，后者帮助你把模型补成一个真正能跑通的系统。

## 2) 这是什么

这里的 “Web Browser” 更准确地说，主要是在学习 **browser engine / rendering engine**，也就是浏览器里负责“把网络资源解释成可见页面”的那一部分。浏览器真正的完整形态还包括标签页、地址栏、历史记录、下载管理、权限系统、扩展系统、多进程隔离等外围能力，但学习项目通常不会一上来就实现这些。

一个最小可学习浏览器，通常会包含下面这些模块：

- URL 与资源加载：知道去哪里拿网页内容。
- HTML 解析：把字符串变成 DOM 树。
- CSS 解析与样式计算：决定每个节点“应该长什么样”。
- 布局：决定每个盒子“应该出现在哪里、占多大”。
- 绘制：把布局结果变成屏幕上的像素。
- 交互：处理点击、键盘、链接跳转、表单提交。
- 进阶部分：JavaScript、事件循环、安全策略、分层合成。

所以，这类项目的本质不是做“一个应用”，而是借由实现这些模块，理解 Web 平台最关键的执行链路。

## 3) 怎么使用

最好的使用方式不是把它当作一本知识手册看完，而是把它当作一个逐步扩张的实验系统来做。建议按下面的顺序学习和动手：

1. 先实现“加载本地 HTML 文本并显示纯文本”。
2. 再把 HTML 解析成树，确认你已经有 DOM 这个中间表示。
3. 加入最基础的 CSS 规则，例如标签选择器、类选择器、颜色、字体大小。
4. 实现最小布局系统，先只支持块级布局，再考虑行内文本换行。
5. 实现绘制，把背景、边框、文字真正画到窗口或画布上。
6. 加入链接点击、页面跳转、表单提交，理解“交互会如何重新触发解析、布局和绘制”。
7. 最后再尝试引入 JavaScript、事件循环、定时器、DOM 更新等更复杂能力。

实践时有两个很重要的方法：

- 每做完一个阶段，都拿一个极小的 HTML 页面做可视化验证。不要一开始就拿真实网站测试，否则你分不清是自己的模型没建立好，还是站点本身太复杂。
- 每实现一个模块，都问自己一个问题：**这个模块的输入是什么，输出是什么，下游模块为什么需要它。** 浏览器的难点不只在功能多，更在于这些中间表示彼此如何衔接。

如果你只是想建立认知框架，优先读 `Browser Engineering` 的目录结构；如果你想尽快获得“我真的把页面画出来了”的反馈，优先从 `Let's build a browser engine` 入手。

## 4) 核心原理

浏览器最核心的原理，可以概括成一句话：**把远端资源逐步转换为结构、样式、几何和像素，并在用户交互后重复这个过程。**

### 4.1 资源加载：从 URL 到字节流

浏览器的起点不是 HTML，而是 URL。URL 告诉浏览器协议、主机、路径和参数。真实浏览器会进一步经过 DNS、TCP、TLS、HTTP 缓存、重定向、压缩协商等流程；学习项目通常会把这里简化成“发一个请求，拿到响应体”。

这一层最重要的理解不是网络细节本身，而是：

- 浏览器拿到的原始输入其实只是字节流。
- 后面所有 DOM、CSS、布局、绘制，都是对这段字节流的逐层解释。
- 同一份字节流，如果 MIME 类型不同，浏览器会走完全不同的处理路径。

### 4.2 HTML 解析：从文本到 DOM 树

HTML 解析的输出是 DOM 树。DOM 不是“原始 HTML 的复制品”，而是浏览器内部可操作的数据结构。你写在 HTML 里的标签、属性、文本节点，会被转成一个树形结构，后续样式、布局、脚本都依赖它。

这里最关键的认识有三点：

- HTML 不是严格的上下文无关语言，真实浏览器会做大量错误恢复。
- 浏览器面对的不是“理想输入”，而是各种缺标签、错嵌套、不规范文档。
- DOM 是“渲染”和“脚本操作”的共同基础，因此它必须稳定、可遍历、可更新。

也就是说，解析器不仅是在“读文本”，更是在为后面所有阶段建立统一世界模型。

### 4.3 CSS 解析与样式计算：从规则到最终样式

CSS 解析会把样式表变成规则集合，但这还不够。真正关键的是 **style calculation**：浏览器要回答“对于 DOM 树上的这个节点，最终生效的样式究竟是什么”。

这个过程会涉及：

- 选择器匹配：哪条规则命中了当前节点。
- 优先级比较：标签、类、ID、内联样式谁更强。
- 继承：某些属性会从父节点传下来，例如字体相关属性。
- 默认值：没有显式声明时，用浏览器默认样式补齐。

很多前端问题本质上都是样式计算问题，而不是“CSS 没生效”。当你自己实现过一次 cascade、specificity 和 inheritance，就会更清楚为什么同样一句 CSS，在不同结构下结果完全不同。

### 4.4 布局：从树到几何

布局阶段回答的是：每个元素的盒子应该放在哪里、多宽、多高。这里会把“有样式的 DOM 节点”继续转成可计算位置和尺寸的布局对象。

toy browser 通常先实现最基础的几个概念：

- 盒模型：content、padding、border、margin。
- 块级布局：元素从上到下堆叠。
- 行内布局：文字如何分词、换行、计算行高。
- 视口坐标：页面坐标怎样映射到屏幕位置。

布局是浏览器里非常关键的一道分水岭。到这一步之前，你知道“页面有什么”；到这一步之后，你才知道“页面在哪里”。很多性能问题也正是在这里出现，例如频繁改动 DOM 或样式会触发重新布局。

### 4.5 绘制：从几何到像素

绘制阶段会根据布局结果生成屏幕上的视觉输出。最小实现通常只需要支持几类绘制命令：

- 绘制背景色和边框。
- 在指定坐标绘制文本。
- 按顺序把所有命令画到一个画布或窗口。

这里要理解的重点是：浏览器不是“边解析边直接往屏幕乱画”，而是先建立结构，再计算样式，再决定位置，最后才绘制。现代浏览器还会把绘制进一步拆成 display list、raster、compositing 等更细的阶段，以支持滚动、动画和 GPU 加速。

### 4.6 交互与重排：页面不是一次性结果

浏览器不是静态渲染器，用户点击链接、输入表单、触发脚本后，页面会更新。一次点击可能导致：

- 导航到新页面，重新经历加载、解析、布局、绘制。
- 修改 DOM，触发重新样式计算。
- 改变几何，触发重新布局。
- 只改变颜色或透明度，可能只需重绘，不必重新布局。

这就是为什么真实浏览器需要事件循环、任务队列、定时器和渲染调度机制。用户看到的“网页会动、会响应”，背后是一个持续运行的状态机，而不是一次性脚本。

### 4.7 现代浏览器为什么远比 toy browser 复杂

学习项目通常故意省略很多工业级难点，但这些恰恰决定了现代浏览器的复杂性：

- JavaScript 引擎：解析、解释、JIT、垃圾回收。
- 安全边界：同源策略、Cookie、CSP、XSS/CSRF 防御。
- 多进程模型：标签页隔离、崩溃恢复、权限收缩。
- 合成与 GPU：动画、滚动、图层优化。
- 标准兼容性：海量历史包袱和边缘行为。

因此，toy browser 的价值不在于“简化版复刻产品”，而在于把不可见的内部机制压缩到一个人可以真正看懂和实现的规模。

## 5) 适用场景

这个学习主题尤其适合下面几类场景：

- 前端工程师想真正理解 DOM、CSS、重排重绘、事件循环，而不是只会调用 API。
- 系统方向学习者想做一个跨网络、编译、图形、运行时的综合项目。
- 做性能优化的人想建立“浏览器为什么会慢”的内部因果模型。
- 做安全的人想理解 Cookie、同源策略、脚本执行和页面隔离为什么必须存在。
- 教学或面试准备中，需要一个能把 Web 平台各层串起来的完整案例。

如果你已经长期在写网页，但总觉得浏览器像个黑箱，这个主题会非常有价值，因为它会把“浏览器替你做了什么”拆成一段段可验证的机制。

## 6) 不适用边界

这个方向也有很明确的不适用边界，最好一开始就知道：

- 它不适合拿来做生产级浏览器。真正浏览器是多年积累的工业系统，不是几千行教程代码能替代的。
- 它不适合用来完整渲染现代大型网站。真实站点依赖复杂 JavaScript、异步资源加载、现代 CSS、无障碍树、媒体解码等大量能力。
- 它不适合只想“快速上线一个功能”的人。做 toy browser 的回报主要是理解，而不是业务交付。
- 它不适合把所有规范一次学完。Web 标准极其庞大，学习时必须主动裁剪，只抓主链路。

简单说，**它是一个高价值的理解型项目，不是一个高性价比的产品型项目。**

## 7) 为什么它重要

浏览器是现代软件世界里最重要、也最容易被误解的运行平台之一。你几乎每天都在浏览器里工作，但如果不知道它内部如何把资源变成页面，就很容易把很多现象当成“玄学”。

理解浏览器的重要性主要体现在几个方面：

- 它把前端开发从“会用框架”提升到“理解平台”。框架变化很快，平台原理更稳定。
- 它会显著提高你分析问题的能力。比如为什么某个改动引发卡顿、为什么 CSS 选择器命中了却没显示、为什么点击事件和默认行为冲突。
- 它让你更容易理解性能与安全。很多优化建议和安全约束，如果不理解浏览器内部机制，只会停留在记忆层面。
- 它训练的是一种非常通用的工程能力：把复杂系统拆成多级中间表示，再让每一级只关心自己的职责。

换句话说，学习浏览器不是为了“去写浏览器公司代码”才有意义，而是为了建立一种更底层、更稳固的 Web 认知。

## 8) 建议延伸

学完最小浏览器后，建议沿着下面几条线继续扩展，而不是停在“能显示页面”这一步：

1. 给 toy browser 加入 `http`/`https` 支持，真正走通网络加载。
2. 把 HTML 解析从“理想输入”升级到“容错输入”，体验浏览器的错误恢复逻辑。
3. 给 CSS 加入继承、优先级和更完整的选择器，真正理解 cascade。
4. 实现块级与行内两套布局规则，亲手处理换行、空白折叠和行高。
5. 加入链接、表单和历史记录，理解导航模型和用户交互。
6. 加入最小 JavaScript 执行环境，感受 DOM 更新如何影响样式、布局和重绘。
7. 学习同源策略、Cookie、XSS、CSRF，补上“浏览器为什么必须保守”的安全视角。
8. 对照真实工程阅读 Servo、WebKit 或 Chromium 的局部实现，看看 toy model 在工业系统里是如何被放大、拆分和优化的。

如果只选一个最值得继续深挖的方向，我建议优先做 **“样式计算 + 布局 + 重绘触发条件”**。这是最能把前端日常问题和浏览器内部机制直接连起来的一段。
