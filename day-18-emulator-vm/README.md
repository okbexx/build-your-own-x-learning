# Day 18 · Emulator / Virtual Machine

> 🌑 `Emulator / Virtual Machine` 的核心，不是“在软件里假装有一台电脑”，而是把一套**指令语义**、**机器状态**与**时间推进规则**重新实现出来。  
> `ISA / 字节码规范 -> 机器状态 -> 取指 -> 译码 -> 执行 -> 设备/系统事件 -> 可观察行为`

## 这是什么

🧠 先给一句最重要的判断：**Emulator 与 Virtual Machine 都是在软件里构造“另一台可执行机器”，区别主要不在“是不是解释执行”，而在“你想复现谁、隔离谁、兼容谁”。**

很多人第一次接触这两个词时，会把它们简单理解成“仿真器更像游戏机，虚拟机更像 JVM”。这个说法不完全错，但太粗。更清晰的办法，是按三层来理解。

第一层是**目标对象**。

- `Emulator` 更强调“复现一个已经存在的目标系统”。这个目标系统可能是 CHIP-8、Game Boy、NES、x86 PC，也可能是某个历史 CPU、某块芯片、某种外设组合。重点在于：原来的那台机器先存在，仿真器要尽量把它的行为重建出来。
- `Virtual Machine` 更强调“定义一台抽象机器并让程序跑在它上面”。这台机器不一定在现实世界存在过。JVM、Lua VM、BEAM、EVM、WebAssembly Runtime 都属于这一路。重点在于：它先定义一套抽象执行模型，再让不同宿主平台去实现它。

第二层是**兼容边界**。

- 仿真器通常追求的是目标程序的**二进制兼容**或至少是**行为兼容**。同一份 ROM、同一份机器码、同一套内存映射，在宿主机上也要尽可能得到相同结果。
- 虚拟机则更常追求**运行时兼容**。程序不必面向真实硬件写机器码，而是面向一种中间指令、字节码或者受控的系统抽象写逻辑。JVM 字节码、Lua 字节码、EVM opcode 都是这个思路。

第三层是**实现手段**。

- 仿真器可以解释执行，也可以做动态二进制翻译，还可以夹带大量针对硬件特性的特判。
- 虚拟机也可以解释执行，也可以 JIT，也可以直接映射到底层硬件虚拟化能力。

所以，从实现角度看，这两者并不是互斥物。它们的共同本质是：**把“机器”降解成一套可维护的状态转移规则**。CPU 不再是硅片，而是若干寄存器、内存数组、程序计数器、标志位、设备状态和一个不断推进的执行循环。你只要把这些状态及其变化规则写对，机器就“活了”。

再往下分，`Virtual Machine` 其实还能拆成两类：

1. **进程级 VM**：例如 JVM、Lua VM、BEAM。它们通常不试图完整复现一台物理电脑，而是提供一套更适合语言运行时的抽象机器。
2. **系统级 VM**：例如能跑客体操作系统的整机模型。它看起来像“一台完整电脑”，包含 CPU、内存、设备、中断、启动流程，有时还会借助硬件虚拟化扩展。

这时你会看到一个很关键的关系：**Emulator 更偏“兼容历史或异构机器”，System VM 更偏“提供隔离与复用”，Process VM 更偏“提供可移植执行平台”。** 但三者底层都离不开同一件事：维护机器状态，并按规则推进它。

从学习价值看，这个主题特别妙，因为它站在三个世界的交叉点上：

- 它像计算机组成原理，因为你必须理解寄存器、内存、指令编码、总线、时钟。
- 它像编译器，因为你在处理指令解码、字节码设计、分派与优化。
- 它又像操作系统，因为你迟早要面对中断、系统调用、设备模型、时间片与 I/O 语义。

换句话说，写 Emulator / VM，本质上是在做一件很“工程哲学”的事：**用宿主机的软件规则，重建另一套机器现实。**

## 怎么使用

⚙️ 学这个主题，最容易犯的错，是一上来就想做 Game Boy、NES、x86 这种复杂目标。这样会导致你在真正理解“机器状态推进”之前，先被设备细节和调试噪音压垮。更合理的学习路径，是从“抽象机器”逐步走向“真实机器”。

建议按这个顺序推进：

1. 先写一个**最小字节码 VM**。只支持 `LOAD`、`ADD`、`JMP`、`HALT` 之类几条指令，理解“程序就是状态机驱动的指令流”。
2. 再写一个**寄存器型或栈型解释器**。这一阶段重点不是性能，而是把指令编码、程序计数器、标志位和内存读写彻底写明白。
3. 然后做一个**小型仿真器**，最经典是 CHIP-8。因为它有屏幕、键盘、计时器，但复杂度还没有飙到不可控。
4. 再尝试进入 **Game Boy / NES / LC-3** 一类系统，开始感受“CPU 正确”并不等于“整机正确”，设备与时序会成为主战场。
5. 最后再去碰**动态翻译、JIT、系统级虚拟化**。这时你才会真正理解，性能优化不是“把 switch 改快一点”，而是在重新设计执行路径。

一个实用的实践顺序如下：

1. 先定义机器状态结构：寄存器、PC、SP、标志寄存器、内存、运行标记、设备状态。
2. 再定义指令编码：每条指令占几个字节，操作码放哪里，立即数怎么取，大小端如何处理。
3. 写出最朴素的取指-译码-执行循环，只跑 3 到 5 条指令。
4. 增加跳转与条件分支，验证控制流。
5. 增加栈、调用、返回，验证子程序语义。
6. 增加 I/O 或内存映射寄存器，验证“外部世界”进入机器。
7. 最后才考虑性能、调试器、快照、JIT、图形刷新与音频同步。

一个极小的解释执行骨架大致长这样：

```c
while (vm.running) {
    uint16_t instr = mem_read(vm.pc);
    vm.pc += 1;

    uint8_t op = instr >> 12;
    switch (op) {
        case OP_ADD:
            exec_add(&vm, instr);
            break;
        case OP_LOAD:
            exec_load(&vm, instr);
            break;
        case OP_JMP:
            exec_jmp(&vm, instr);
            break;
        case OP_TRAP:
            exec_trap(&vm, instr);
            break;
        case OP_HALT:
            vm.running = 0;
            break;
        default:
            vm.fault = VM_BAD_OPCODE;
            vm.running = 0;
            break;
    }

    tick_devices(&vm);
}
```

上面这段代码看起来平平无奇，但它几乎浓缩了整个主题的核心：**先读状态，再根据指令改变状态，最后推进时间。** 只要这三个环节的语义是稳定的，你的机器就是可解释、可调试、可扩展的。

可以从这组测试开始逼近正确性：

```text
用例 1：LOAD R0, 2; ADD R0, 3; HALT
期望：R0 最终等于 5，PC 停在 HALT 之后

用例 2：LOAD R0, 0; LOOP: ADD R0, 1; CMP R0, 10; JLT LOOP; HALT
期望：R0 最终等于 10，循环次数可预测

用例 3：CALL F; HALT; F: LOAD R1, 7; RET
期望：返回地址压栈并正确恢复，R1 等于 7

用例 4：STORE R2, [0x8000]
期望：如果 0x8000 是内存映射 I/O，应该触发设备副作用，而不只是普通写内存

用例 5：等待定时器中断 60 次
期望：无论宿主机多快，客体计时器语义都稳定，不因宿主 CPU 提速而“时间失真”
```

如果你在做学习项目，我建议采用“**先正确，后逼真，再提速**”的准则：

- 先正确：先确保寄存器、跳转、栈、标志位都对。
- 后逼真：再处理时钟、设备节拍、阻塞输入、中断顺序。
- 再提速：最后考虑 threaded dispatch、block cache、JIT、硬件辅助虚拟化。

很多初学者会把性能当作第一目标，但对 Emulator / VM 来说，**错误地快，远比正确地慢更没价值**。因为一旦语义歪了，你后面所有优化都是在放大偏差。

## 核心原理

🧠 这一部分才是主题的骨架。你真正要掌握的不是“能跑起来”，而是“为什么它会这样跑，为什么少一个机制就会失真”。

### 1. 指令集架构：软件与机器之间的合同

`ISA` 可以理解为机器对外公布的法律文本。它规定了程序可以使用哪些寄存器、有哪些指令、指令怎样编码、标志位如何变化、地址空间多大、内存按字节还是按字寻址、调用约定如何落地、异常如何触发。

这件事为什么重要？因为仿真器和 VM 并不是在“猜测程序想干什么”，而是在**严格执行一份预先定义好的契约**。例如某条 `ADD` 指令，如果规范写明会更新零标志和负标志，那么你就必须更新；如果规范写明某条读取会触发内存映射寄存器副作用，那么你不能偷懒把它当成数组访问。

ISA 的难点不止是“认得 opcode”。真正麻烦的是那些被新手忽略的边缘细节：

- 立即数是否要符号扩展；
- 溢出是静默截断还是设置标志；
- 未对齐访问是允许、修正，还是直接 fault；
- 大小端如何影响指令装载与数据读写；
- 某些保留位写入后是否必须忽略；
- 条件码是基于结果更新，还是基于操作本身更新。

在真实世界里，很多兼容性 bug 就死在这些“看似不重要”的细节里。你以为自己实现的是“差不多的一台机器”，程序却要求的是“细节完全一致的那台机器”。这就是为什么 Emulator 很容易从几百行小项目，一路长成几万行工程。

### 2. 取指-译码-执行循环：一切运行时语义的心跳

几乎所有 CPU 模型和字节码 VM，内核都绕不开同一个循环：

1. 从 `PC` 指向的位置取出下一条指令。
2. 增加 `PC`，或者准备由分支指令覆写它。
3. 解析操作码和操作数字段。
4. 修改寄存器、内存、标志位或设备状态。
5. 推进周期、计时器或中断检查。
6. 进入下一轮。

这个循环看似简单，但里面藏着几个关键点。

第一，`PC` 到底何时递增。很多架构会先取值再自增，但分支类指令又可能覆盖它；有些相对跳转的偏移是基于“当前 PC”，有些是基于“下一条 PC”。这一点错一个时机会导致整个控制流歪掉。

第二，译码到底在哪里做。最朴素的写法是 `switch(opcode)`，优点是直观；进阶一点会做表驱动；再往上可能做 direct threaded dispatch，减少分派开销。但不管形式如何变，**语义上的本质不变：你要把二进制位模式映射成状态变化规则。**

第三，执行不是“算一下结果”这么简单。很多指令的副作用是复合的：既改寄存器，也改条件码；既写内存，也触发设备；既修改流控制，也引入异常可能。一个成熟的实现通常会把“主效果”和“副效果”一起看待，而不是只盯着显式结果。

可以把这个循环理解为软件里的“微型 CPU 核”。如果这一层不稳，上层所有程序行为都会失真。

### 3. 寄存器与内存模型：机器状态到底放在哪里

从软件角度看，一台机器首先不是“会动的”，而是“有状态的”。所谓状态，最核心的就是寄存器文件与内存模型。

寄存器是 CPU 的近身工作台。不同机器会有通用寄存器、程序计数器、栈指针、状态寄存器、浮点寄存器、向量寄存器、控制寄存器。它们的意义不是“多几个变量”而已，而是定义了程序怎样暂存数据、怎样跳转、怎样返回、怎样表达上一次计算的结果。

内存模型则回答三个问题：

1. 地址空间有多大；
2. 地址如何映射到真实存储或设备；
3. 读取和写入会触发什么副作用。

最小学习项目里，内存常被写成一个数组，例如 `uint8_t memory[65536]`。这当然好用，但你很快会发现“内存不是纯数组”：

- 某些地址其实是 ROM，只读不可写；
- 某些地址是 RAM，可读可写；
- 某些地址映射到键盘、显示器、定时器、串口；
- 某些地址读出来的值和设备当前状态有关；
- 某些地址写进去以后会立刻改变外设行为。

一旦进入系统级 VM，这件事会更复杂，因为还会牵扯页表、特权级、TLB、内核空间、用户空间、缺页异常、DMA 可见性等问题。也就是说，**内存不是“存数据的地方”这么简单，它是机器与设备、权限、时间耦合的主战场。**

如果把这层理解透了，你就会明白为什么很多项目调不通时，第一怀疑对象不是 ALU，而是地址映射、栈布局、读写宽度或内存映射寄存器语义。

### 4. 解释执行、线程化分派与二进制翻译：速度从哪里来

最直接的 VM/仿真器实现方式，是解释执行。意思很简单：每遇到一条客体指令，就由宿主机代码解释一次。优点是结构清晰、调试方便、实现成本低；缺点是每条指令都要经历“取指、分派、执行”的宿主开销，性能通常不高。

当系统变大后，你会开始问一个问题：**能不能少解释几次？** 于是优化路线出现了。

第一种常见优化是**线程化分派**。也就是减少 `switch` 的重复判断成本，让执行路径更直接。它不改变语义，只是压缩分派层的额外开销。

第二种是**基本块缓存**。把一段连续客体指令翻译成一段宿主可复用的执行单元，下次跳回来就直接复用，而不是重新逐条解释。

第三种是**动态二进制翻译**，也就是常说的 `DBT` 或某些场景下的 `JIT`。核心思想是：把客体指令序列翻译成宿主机指令序列，缓存起来执行。这样宿主 CPU 跑的就不是“解释器在解释”，而更像“直接跑翻译后的代码”。

但这里有个经常被忽视的工程事实：**翻译越激进，保持正确越难。**

- 你要处理跨块跳转；
- 你要处理自修改代码；
- 你要处理异常回退与精确中断点；
- 你要保证标志位与延迟副作用和原机器一致；
- 你要在宿主优化与客体可观察语义之间维持平衡。

因此，解释执行与翻译执行的关系，不是“前者落后、后者先进”，而是“前者更直接保真，后者更适合追求吞吐”。很多优秀系统其实两者都会混用：冷路径解释，热点路径翻译，异常路径回落。

### 5. 中断、异常与系统调用：外部世界如何打断你的机器

如果一台机器只有顺序执行的指令流，它离“真实计算环境”还差得很远。现实中的程序总会遇到三类事件：

1. **异常**：例如除零、非法指令、缺页、访问越界。这些通常是同步发生的，因为它们由当前指令直接触发。
2. **中断**：例如定时器到了、键盘来了输入、磁盘完成了 I/O。这些通常是异步事件，会在某个边界切入当前执行。
3. **系统调用 / trap**：程序主动请求更高权限或更高层服务，例如打印字符、读文件、申请内存、退出程序。

很多学习型 VM 会先把系统调用写成一组 `TRAP` 指令，这非常好，因为它能让你直观看到：**程序并不能直接碰世界，它只能通过受控入口请求世界帮它做事。**

对于仿真器来说，中断处理尤其关键。因为一旦你引入键盘、显示器、声卡、定时器、DMA 或图形刷新，就必须回答：

- 中断在什么时候被采样；
- 屏蔽位何时生效；
- 当前指令执行到一半时是否允许插入；
- 返回现场如何保存；
- 不同优先级的事件怎么排序。

对于系统级 VM，这一层还会继续扩展成“客体系统调用如何映射到宿主内核服务”。你可能选择完整仿真内核 ABI，也可能选择半虚拟化接口，也可能完全交给硬件辅助虚拟化。无论哪种方案，核心矛盾都一样：**既要给客体程序“像真的一样”的世界，又不能真的把宿主机裸露给它。**

### 6. 时钟、节拍与确定性：为什么“跑得快”不等于“时间对”

很多新手把“程序能出结果”当作仿真完成，但只要涉及游戏机、操作系统、音频、图形、网络协议或并发运行时，时间模型立刻变成决定成败的部分。

真实机器不是无限快地瞬间完成一切，而是在时钟节拍下推进。哪怕你的宿主机比目标机器快一万倍，你也不能简单让客体逻辑“能跑多快就跑多快”，否则就会出现：

- 游戏速度过快；
- 音频节奏错乱；
- 定时器中断频率错误；
- 轮询逻辑失效；
- 动画帧与输入采样不同步。

因此，很多 Emulator / VM 都要定义一种“客体时间”。这个时间可以按周期、按指令数、按帧、按定时器 tick 来推进。关键不在形式，而在于它必须和设备模型统一。

这里最重要的概念不是快慢，而是**确定性**。所谓确定性，就是在相同输入下，机器状态演化顺序应当稳定可复现。如果今天按一个按键会成功、明天同样输入却随机失败，那你几乎没法调试。也正因如此，很多高质量仿真器特别重视：

- 固定步进；
- 精确的事件排队；
- 帧与 CPU 周期的对应关系；
- 输入采样时机；
- 快照与回放能力。

在大型系统里，性能优化最终也要服从这个原则：你可以让机器跑得更快，但不能让时间语义跑偏。

### 7. 设备模型：没有外设，机器只是半成品

只实现 CPU 指令，往往只能证明“核心算术和控制流是对的”。一旦要运行真正有交互的程序，你就必须给机器接上设备。

设备模型最常见的接入方式有两种：

1. **内存映射 I/O**：把设备寄存器暴露在某段地址空间里，CPU 对这些地址的读写就是在操作设备。
2. **端口映射 I/O**：通过专门的输入输出指令与设备交互。

这层最难的不是“多写几个回调”，而是把设备的行为嵌进统一的时间线里。比如显示器何时刷新、键盘何时采样、串口是否阻塞、DMA 是否与 CPU 并发、音频缓冲什么时候欠载，这些都不能只靠静态数据结构表达。

所以你会发现，设备模型本质上是在说：**机器不只是执行指令，还要持续与外部世界交换状态。** 一旦这层被简化得过头，很多程序就会表现出“能启动，但不可信”的假成功。

### 8. 调试器、快照与可观测性：会跑只是起点，会看见才算掌控

Emulator / VM 项目非常适合培养“可观测性设计”意识。因为这类系统一旦出错，表面症状通常很远，真正根因可能发生在几千条指令之前。

因此，成熟实现一般都会有几类调试能力：

- 单步执行；
- 断点；
- 寄存器和内存转储；
- 指令 trace；
- 设备事件日志；
- 快照保存与恢复；
- 与参考实现做 diff。

为什么快照这么有价值？因为机器状态一旦能被完整序列化，你就能把“偶现 bug”冻结在某一刻。然后你可以重复载入、重复单步、重复比较，而不用每次都从冷启动跑到问题点。这对复杂仿真器几乎是救命能力。

从学习角度说，这一层还有一个更深的价值：它会逼你把“机器状态究竟包含什么”想清楚。凡是你保存不了、比较不了、解释不了的状态，往往说明你的模型还没真正收束。

## 适用场景

🛰️ `Emulator / Virtual Machine` 非常适合以下场景：

- **学习计算机底层原理**：它把“程序如何在机器上运行”这件事具体化了，不再只是课本名词。
- **跨平台运行**：用一套字节码或抽象机器隔离底层硬件差异，让程序只写一次，多处运行。
- **历史软件保存与复现**：旧游戏、旧固件、旧系统、旧工具链往往只能靠仿真继续活下去。
- **隔离与安全执行**：沙箱、智能合约运行时、插件系统、受限脚本环境，本质上都在借 VM 收口能力。
- **测试与调试**：在可控、可回放、可注入故障的环境里验证底层程序，比直接上真机更稳。
- **二进制分析与逆向工程**：仿真能帮助你观察未知程序在受控环境中的状态变化。
- **云端或浏览器内运行传统程序**：当宿主平台不支持目标二进制时，仿真与 VM 是重要桥梁。

## 不适用边界

🚫 它也不是银弹，至少有这些边界：

- **极端追求原生性能且语义必须贴近宿主硬件时**：多一层解释或翻译几乎必然带来开销。
- **目标系统复杂到图形、驱动、总线时序都要求极高保真，而你又没有足够资料时**：项目会迅速失控。
- **只是想做一个普通业务系统，却误把“自造 VM”当必要基础设施时**：抽象层过多反而制造维护负担。
- **目标程序严重依赖真实硬件副作用、未定义行为或闭源外设协议时**：缺失细节会让兼容性很脆。
- **你并不需要二进制兼容，只需要逻辑迁移时**：直接重写或转译可能更便宜。
- **涉及 ROM、固件、商业软件镜像时**：法律授权与分发边界必须单独处理，技术可行不等于可公开使用。

一个很实用的判断标准是：**你的目标到底是“重建原机器”，还是“提供一个可控执行层”**。如果两者都不是，就不要为了“看起来高级”而引入 Emulator / VM。

## 为什么它重要

⚡ 这个主题重要，不是因为它酷，而是因为它逼你正面理解“程序执行”到底是什么。

平时我们写代码，很容易默认底层世界已经存在：CPU 会跑、内存会存、调用会返回、时间会前进、输入会到来、系统调用会成功。但在 Emulator / VM 里，这一切都不是前提，而是你要亲手定义的机制。你会第一次真切意识到：所谓程序运行，本质上只是**一连串对状态的受控更新**。

它的重要性还在于，它把很多分散的基础课知识重新焊接起来了。

- 你学过计算机组成原理，但写 Emulator 时才真正明白寄存器、PC、标志位和指令编码怎么联动。
- 你学过操作系统，但实现中断、trap、内存映射 I/O 时才真正感到“系统边界”有多具体。
- 你学过编译器或解释器，但做字节码 VM 时才真正把“语义执行”与“调度开销”放到一个工程问题里。

更进一步说，Emulator / VM 训练的是一种非常高级的工程能力：**为另一个世界定义规则，并保证这个世界在不可信输入下仍然可预测。** 这和做数据库、容器、浏览器、区块链执行环境、沙箱、插件系统、游戏引擎，其实有很深的共通性。你都在设计一套受控运行时，区别只在于规则边界、状态规模与性能目标不同。

很多工程师一旦真正写过一个 VM，再回头看语言运行时、JavaScript 引擎、数据库查询执行器、容器隔离层，会突然获得一种“通了”的感觉。因为他们终于看见：这些系统虽然表面不同，但底层都在做同一类事：**定义状态、解释规则、推进时间、处理外部事件。**

## 建议延伸

🌌 如果你已经做完一个最小版本，后续不要平均撒网，建议沿着下面几条线继续加深：

1. **从字节码 VM 走向真实 ISA**  
思考问题：为什么自己设计的字节码通常比真实 CPU ISA 更“干净”，而真实 ISA 却更难完全仿真？

2. **从解释执行走向 JIT / 动态翻译**  
思考问题：当你把客体代码翻译成宿主代码时，哪些“语义时刻”必须被精确保留，不能被随便优化掉？

3. **从 CPU 走向整机**  
思考问题：为什么很多仿真器 CPU 指令都实现对了，机器还是启动不了？究竟是设备、中断、内存映射，还是时钟出了问题？

4. **从功能正确走向时间正确**  
思考问题：如果同一份程序结果看起来对，但节奏、输入响应或音频不同步，它还算“正确”吗？

5. **从单步调试走向快照与回放**  
思考问题：一个复杂系统为什么必须具备“冻结状态”的能力？没有快照时，你调试的成本会如何指数上升？

6. **从语言运行时看 VM 设计**  
思考问题：为什么 Lua VM、JVM、BEAM、EVM 都叫 VM，但它们的指令设计、内存策略和系统边界会差这么多？

7. **从虚拟化看系统工程边界**  
思考问题：当硬件已经支持虚拟化扩展，纯软件仿真还剩下什么不可替代的价值？

如果想给自己设一条很扎实的进阶路线，我推荐这样排：

1. 先做一个最小寄存器型 VM。
2. 再做 CHIP-8。
3. 再读一个 LC-3 或 Game Boy 项目。
4. 然后补动态翻译、JIT、系统级虚拟化资料。
5. 最后尝试给你的 VM 加调试器、快照和指令 trace。

只要你真的把这条线走通，你对“计算机为什么能运行程序”这件事的理解，会比只看概念图深很多。

## 结尾金句

> 🌑 真正的 `Emulator / Virtual Machine` 不是把另一台机器“画出来”，而是把它的**规则、状态与时间**在你的程序里重新点亮。  
> 当你能亲手让一台并不存在于眼前的机器稳定运行时，你理解的就不再是某个工具，而是“计算本身如何成立”。
