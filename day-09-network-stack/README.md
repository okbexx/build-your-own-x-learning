# Day 9 · Network Stack

## build-your-own-x 对应原始项目地址

`build-your-own-x` 中与本主题对应的入口是：

https://github.com/codecrafters-io/build-your-own-x#build-your-own-network-stack

这个链接的价值不只是“给你一个仓库”，而是给你一个按主题筛选过的入口。工程上更合理的做法通常不是一上来就追求完整 TCP/IP 实现，而是先从一个教学型、层次清晰、能跑通最小链路的项目开始，再逐步补齐 ARP、IP、ICMP、UDP、TCP、路由、重传和校验等能力。

## 这是什么

Network Stack，直译是“网络协议栈”，本质上是一套分层协作的通信系统。应用程序并不直接“发网线上的比特”，而是把数据一层层向下交给传输层、网络层、链路层；接收时再一层层向上还原。

如果自己动手实现一个网络栈，真正学习到的不是几个协议名词，而是下面这些工程问题：

- 数据包在内存里如何表示和解析。
- 每一层如何定义输入、输出和状态机。
- 校验和、序列号、端口、路由表这些字段为什么存在。
- 阻塞、超时、重传、乱序、分片等异常情况如何处理。
- 用户态协议实现和内核协议栈之间的边界在哪里。

## 怎么使用

如果你的目标是“学懂”，推荐按下面顺序使用这类项目，而不是直接读完整代码：

1. 先确定项目覆盖的层级。
   例如它只是实现 Ethernet + ARP + IPv4，还是已经包含 UDP/TCP，甚至带 socket 接口模拟。
2. 先跑通最小链路。
   至少要能看到一个包从构造、封装、发送、接收、解包的完整路径。
3. 带着抓包工具一起读。
   一边看代码，一边用 `tcpdump` 或 Wireshark 对照头部字段，理解“代码里的结构体”如何变成“线上真实数据包”。
4. 按协议层拆着看。
   不要从主函数一路顺着读到底，应该按 `ARP -> IP -> ICMP/UDP/TCP` 的顺序分块理解。
5. 自己改一个行为验证理解。
   例如故意改错 TTL、校验和、端口号、序列号，观察对端或抓包结果如何变化。

工程上最有效的用法不是“看懂别人怎么写”，而是“改一处，验证一处”。网络栈很容易看起来懂了，实际上只要一改字段就暴露理解是否扎实。

## 核心原理

网络栈最关键的不是协议条目多，而是分层、封装、寻址、可靠性和状态管理这几个核心思想。

1. 分层

每层只解决自己那一层的问题：

- 链路层关心同一链路上的帧怎么发。
- 网络层关心跨网络寻址和转发。
- 传输层关心进程到进程的通信，以及是否需要可靠传输。

分层的好处是可替换。上层不需要知道网卡细节，下层也不需要理解 HTTP 语义。

2. 封装与解封装

应用数据向下传递时，每层都会加自己的头部：

- 传输层加端口、序列号、确认号。
- 网络层加源/目标 IP、TTL、协议号。
- 链路层加源/目标 MAC、帧类型。

接收时反过来逐层剥离。工程上这要求你清楚区分“有效载荷”和“协议头”，否则偏移量、长度、校验都容易出错。

3. 寻址

网络栈里至少有两类地址：

- MAC 地址用于本地链路投递。
- IP 地址用于跨网络定位主机。

这也是 ARP 存在的原因：应用或 IP 层知道目标 IP，但真到发帧时还需要目标 MAC，所以必须做地址解析。

4. 路由与转发

不是所有目标都在本地子网。若目标不在本地，就不能直接找目标 MAC，而是要把包交给下一跳。也就是说，IP 层真正决定的是“这个包下一步该发给谁”，不是“最终主机的物理地址是什么”。

5. 可靠性不是 IP 自带的

IP 只负责尽力而为投递，不保证到达、不保证顺序、不保证不重复。真正的可靠性通常由 TCP 提供，核心机制包括：

- 序列号：识别字节流位置。
- 确认应答：告诉对方哪些数据已经收到。
- 重传：超时后补发丢失数据。
- 滑动窗口：控制在途数据量。
- 流量控制与拥塞控制：避免把接收端或网络压垮。

这也是为什么“能发包”离“能稳定通信”还差很远。

6. 状态机

网络协议不是简单的请求-响应函数调用，而是状态机。以 TCP 为例，连接建立、数据传输、关闭连接都依赖状态转换。自己写协议栈时，很多 bug 不是字段写错，而是状态推进顺序错了，导致边界场景失效。

## 适用场景

自己实现网络栈，适合下面这些场景：

- 学习操作系统、计算机网络、协议设计时，需要把抽象概念落到代码和真实数据包上。
- 做高性能网络、用户态协议、DPDK、eBPF、虚拟交换机等方向前，需要建立底层直觉。
- 调试复杂网络问题时，希望理解“一个包到底经过了哪些层、在哪一层出错”。
- 做嵌入式、unikernel、教学操作系统或实验型内核时，需要裁剪或自定义协议能力。

## 不适用边界

这类项目很适合学习，但不适合直接当生产网络基础设施使用，边界要分清：

- 教学型实现通常不完整，协议覆盖面有限。
- 很多实现省略异常处理，对乱序、丢包、分片、拥塞、MTU 变化支持不足。
- 安全能力通常不够，没有经过长期对抗性验证。
- 性能不一定好，很多代码为了易懂牺牲了零拷贝、批处理、锁优化和 NUMA 友好性。
- 即使功能上“能通”，也不代表兼容各种真实网络设备和复杂拓扑。

工程上应把它当作“理解模型”和“实验平台”，而不是替代 Linux 内核协议栈。

## 为什么它重要

网络栈的重要性在于，它把很多日常开发里被隐藏掉的事实重新暴露出来。

平时调用一个 `connect()`、`send()`、`recv()` 很容易误以为网络通信就是几个 API；但真正决定系统行为的，是下面这些底层机制：

- 包是否真的发出去了。
- 对端为什么没回。
- 是 DNS、ARP、路由、握手、重传还是 MTU 导致问题。
- 为什么本地能通、跨网段不通。
- 为什么延迟抖动会把上层服务拖垮。

理解网络栈之后，很多线上问题会从“黑盒玄学”变成“可以定位的链路问题”。这对后端、基础设施、SRE、系统工程师都非常关键。

## 建议延伸

如果这一节学完，建议继续向下面几个方向延伸：

1. 抓包验证。
   用 Wireshark 把自己实现的 ARP、ICMP、TCP 三次握手逐个对照字段看清楚。
2. 补一个最小 TCP。
   不要求完整高性能，先把建连、收发、重传、挥手跑通。
3. 理解内核接口。
   继续看 `socket`、`TUN/TAP`、raw socket，弄清用户态代码如何接入真实网络设备。
4. 对比 Linux 实现。
   不必一开始硬啃全部源码，但可以定向看 `net/ipv4`、`net/core` 相关路径，建立“教学版”和“工业版”的差距认识。
5. 结合性能主题学习。
   后续可以把网络栈和 epoll、零拷贝、RSS、XDP、DPDK 放在一起理解，形成从协议到性能优化的完整链路。

如果只停留在“知道 TCP/IP 分层”，收获其实很有限；真正的进步来自把协议字段、状态机、抓包结果和代码执行路径对应起来。
