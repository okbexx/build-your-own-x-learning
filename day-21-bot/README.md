# Day 21 · Build Your Own Bot

> `DARK TERMINAL // SIGNAL ONLINE`
>
> 在很多人的想象里，Bot 只是一个“会回话的小程序”。  
> 但从工程视角看，Bot 更像一台持续监听环境、解释输入、维护内部状态、再把决策投射回外部世界的微型自动体。  
> 它不一定聪明，却一定要**稳定、可控、可迭代**。 🤖

---

## 一、Bot 的核心概念与分类

Bot，中文常被翻译为“机器人程序”或“自动代理”，本质上不是一个单一产品形态，而是一类**能够接收事件、做出判断、执行动作**的软件实体。它的关键不在于有没有自然语言能力，而在于它是否具备了“感知输入 -> 处理逻辑 -> 触发输出”的最小闭环。

如果把普通脚本看成一次性执行的命令，那么 Bot 更像一个常驻在暗处的进程：它等待信号、解释上下文、根据规则或模型改变自己的行为。正因如此，Bot 的设计重点从来不只是“能不能回复一句话”，而是“在持续运行中如何保持一致性、可观察性与边界感”。

### 1. 聊天机器人

这是最常见的一类 Bot。它出现在 IM、客服系统、社群平台、终端助手、知识问答入口中。  
它的核心任务是把用户的文本、语音、按钮点击等输入，转化成可理解的意图，再生成合适的响应。

聊天机器人可以很简单，只做关键词匹配：

```text
用户: /help
Bot : 返回命令说明
```

也可以很复杂，具备上下文记忆、工具调用、知识检索、长对话维护能力。  
但不论复杂度如何，它都绕不开两个根问题：

- 它怎么理解“用户想干什么”？
- 它怎么决定“现在应该说什么”？

### 2. 自动化 Bot

自动化 Bot 并不强调对话能力，而强调**任务执行**。  
比如 CI 通知 Bot、监控告警 Bot、群管 Bot、表单流转 Bot、自动回帖 Bot、定时交易 Bot，都属于这一类。

这类 Bot 的价值不在“像人”，而在“像基础设施的一根延长触手”：

- 它监听事件
- 它判断条件
- 它调用接口
- 它回写结果

从结构上看，它更接近事件驱动的工作流引擎，而不是拟人聊天体。

### 3. 游戏 AI Bot

游戏中的 Bot 往往被误解成“假的玩家”，其实它更准确的定义是**被程序控制的决策代理**。  
它可能负责敌人巡逻、追踪玩家、释放技能、资源采集、路径规划，甚至在竞技场景中模仿人的策略行为。

这类 Bot 常见的核心机制包括：

- 有限状态机（巡逻、警觉、追击、撤退）
- 行为树
- 路径搜索
- 规则评分
- 强化学习或策略网络

游戏 AI Bot 的重点不是“会说话”，而是“在有限感知下做出看起来合理的行动”。  
它让我们意识到：Bot 的本质并不是聊天，而是**自动决策**。

### 4. 爬虫 Bot

爬虫 Bot 是互联网世界里最典型的“非人格化 Bot”。  
它的输入不是用户消息，而是网页、接口、DOM、链接图、反爬策略；它的输出不是语言，而是数据抓取、页面解析、任务队列推进。

从工程角度看，爬虫 Bot 是一种面向信息采集的自动体。它通常包含：

- URL 调度
- 请求控制
- 内容抽取
- 去重与存储
- 失败重试
- 频率限制

当网站开始识别异常访问模式时，爬虫 Bot 还必须面对身份伪装、节奏控制、浏览器模拟等更复杂的问题。

### 5. Bot 的分类方式，不止按场景

除了按用途分类，Bot 还可以从系统形态继续拆分：

- 按交互方式分：命令式、对话式、GUI 驱动式、API 驱动式
- 按控制逻辑分：规则型、状态机型、模型型、混合型
- 按运行方式分：轮询型、Webhook 型、事件流型、常驻代理型
- 按自治程度分：被动响应、半自动执行、主动规划、目标驱动

这很重要，因为真正决定工程难度的，往往不是“它属于哪一类业务”，而是**它如何接入世界、如何管理状态、如何承受不确定输入**。

## 二、Bot 的通用架构

一个可用的 Bot，表面上看只是“收消息然后回消息”，但底层通常可以抽象成一条稳定的处理流水线：

```text
[输入解析] -> [意图识别] -> [状态管理] -> [响应生成] -> [输出执行]
```

这个结构之所以重要，是因为它把“看起来像魔法的交互行为”拆回到了五个可工程化模块。你不一定每个 Bot 都需要完整实现全部层次，但只要系统开始变复杂，这五层迟早会出现。

### 1. 输入解析

输入解析负责把外部世界的不规则信号，转换成程序内部能消费的统一事件对象。  
外部输入可能是：

- 一条聊天消息
- 一个 Slash Command
- 一个按钮点击
- 一个网页元素变化
- 一个定时器触发事件
- 一次游戏状态更新

解析层解决的是“格式问题”，不是“语义问题”。  
例如，把原始平台 payload 转换成如下统一结构：

```python
event = {
    "source": "telegram",
    "user_id": "u_42",
    "channel_id": "g_7",
    "text": "/deploy prod",
    "timestamp": 1778544000,
}
```

如果这一层设计得混乱，后面的意图识别和状态管理就会被平台细节污染，Bot 会越来越难维护。

### 2. 意图识别

意图识别关注的是：“这段输入到底想触发什么行为？”

最轻量的方式是前缀命令和关键词匹配：

- `/help` -> 帮助
- `/ping` -> 健康检查
- `重启服务` -> 运维命令

更进一步可以做：

- 正则提取参数
- 模板槽位填充
- 分类器判断意图
- NLU/LLM 解析自然语言目标

这里的核心原则不是“识别得多聪明”，而是“识别结果要足够可执行”。  
也就是说，最终最好落成一种结构化形式，例如：

```json
{
  "intent": "deploy_service",
  "slots": {
    "env": "prod"
  }
}
```

只有当语义被压缩成结构化指令，后续模块才能稳定运行。

### 3. 状态管理

Bot 一旦不是“一问一答即忘”，状态就会变成核心问题。  
状态可能包括：

- 用户会话上下文
- 当前对话阶段
- 上一次执行结果
- 任务队列位置
- 限流计数器
- 游戏中的行为模式

很多初学者写 Bot 时，只关注“收到消息怎么回”，忽略了 Bot 在连续交互中的身份。  
实际上，没有状态管理的 Bot，最多只是一个回调函数；有状态管理的 Bot，才真正像一个持续存在的系统。

最常见的状态实现方式包括：

- 内存字典：适合原型
- Redis：适合会话和计数器
- 数据库：适合持久任务与审计
- 显式状态机：适合分阶段流程

### 4. 响应生成

响应生成是把“识别出的意图 + 当前状态 + 可用工具结果”转化为下一步动作。  
注意，这里的“响应”不一定是文字，它可以是：

- 返回一段文本
- 调用一个 API
- 执行一个系统命令
- 点击一个网页按钮
- 切换游戏 AI 状态
- 推送一条告警消息

因此，响应生成更准确地说，是**决策生成**。  
它可以基于规则：

```text
if intent == "help":
    return show_help()
```

也可以基于模板、检索系统、规划器，甚至 LLM。  
但工程上必须警惕一点：输出越自由，失控风险越高。  
好的 Bot 往往不是“什么都能说”，而是“在该收敛的地方严格收敛”。

### 5. 输出执行

输出执行把内部决策投射回外部环境。  
这一层通常要面对最真实的世界约束：

- 平台 API 限流
- 网络失败
- 幂等问题
- 重试风暴
- 权限边界
- 真实副作用

例如，一个“删除消息”的动作，不只是发个请求那么简单，还涉及：

- 这条消息是否存在
- 当前 Bot 是否有删除权限
- 重试后会不会重复触发
- 失败后是否需要补偿

所以，输出执行层是 Bot 从“逻辑体”变成“行动体”的接口面，也是故障最密集的地方。

### 6. 为什么这个架构通用

因为无论是聊天 Bot、运维 Bot、游戏 Bot 还是爬虫 Bot，它们都在做同一件事：

> 从环境接收事件，对事件建立解释，结合内部状态形成决策，再把决策施加回环境。

这正是自动代理系统的最小骨架。  
你可以把模型替换掉，可以把平台换掉，可以把输出从“发消息”换成“执行动作”，但这条主链几乎不会变。

## 三、从零实现一个极简 Bot 的关键代码思路

下面不追求可直接上线的完整工程，而是展示一个最小可工作的 Bot 结构。  
目标是让你看到：**Bot 不是一堆散乱回调，而是一个由事件循环、命令解析、状态机共同支撑的长期进程。** ⚙️

### 1. 极简设计目标

我们假设要实现一个终端里的小型聊天 Bot，支持：

- 接收用户输入
- 解析 `/help`、`/set name xxx`、`/echo xxx`
- 维护一个最小会话状态
- 根据状态决定响应
- 持续运行直到 `/quit`

### 2. 事件循环

事件循环是 Bot 的心跳。  
没有循环，Bot 只是函数；有了循环，它才变成常驻代理。

```python
class Bot:
    def __init__(self):
        self.running = True
        self.state = {
            "name": "operator",
            "mode": "idle",
        }

    def poll_event(self):
        text = input(">> ").strip()
        return {"type": "message", "text": text}

    def run(self):
        while self.running:
            event = self.poll_event()
            action = self.handle_event(event)
            self.execute(action)
```

这里最重要的不是 `input()` 本身，而是这个思想：

- 先拉取事件
- 再处理事件
- 再执行结果
- 然后回到下一轮

未来把 `input()` 换成 Webhook、消息队列、Socket、游戏帧更新、浏览器事件流，结构依然成立。

### 3. 命令解析

命令解析的目标，是把字符串压缩成结构化指令。  
原始文本不适合直接驱动业务逻辑，因为它太松散、太容易分支爆炸。

```python
def parse_command(text: str) -> dict:
    if text == "/help":
        return {"intent": "help"}

    if text == "/quit":
        return {"intent": "quit"}

    if text.startswith("/echo "):
        return {"intent": "echo", "args": {"message": text[6:]}}

    if text.startswith("/set name "):
        return {"intent": "set_name", "args": {"name": text[10:]}}

    return {"intent": "unknown", "raw": text}
```

这一层虽然看起来简单，却是复杂 Bot 的雏形。  
后续可以把它升级为：

- 正则路由器
- 命令树
- DSL 解析器
- NLU 分类器
- LLM function calling

但无论形式如何变化，原则不变：**输入先结构化，再进入决策层。**

### 4. 用状态机控制行为

Bot 的状态机不是为了“显得高级”，而是为了避免流程失控。  
比如用户刚进入系统时处于 `idle`，如果进入配置流程，状态变成 `configuring`；完成后再退回 `idle`。

```python
def transition(state: dict, intent: str, args: dict | None = None):
    args = args or {}

    if intent == "help":
        return state, {"type": "reply", "text": "可用命令: /help /echo /set name /quit"}

    if intent == "set_name":
        new_state = dict(state)
        new_state["name"] = args["name"]
        return new_state, {"type": "reply", "text": f"identity updated: {args['name']}"}

    if intent == "echo":
        prefix = state["name"]
        return state, {"type": "reply", "text": f"[{prefix}] {args['message']}"}

    if intent == "quit":
        return state, {"type": "shutdown"}

    return state, {"type": "reply", "text": "unknown command"}
```

在这个模型里，状态转移和响应生成是绑在一起的：

- 当前状态决定允许什么动作
- 动作可能修改状态
- 新状态影响下一轮响应

这就是一个最小状态机。

### 5. 把处理链条接起来

```python
class Bot:
    def __init__(self):
        self.running = True
        self.state = {"name": "operator", "mode": "idle"}

    def poll_event(self):
        text = input(">> ").strip()
        return {"type": "message", "text": text}

    def handle_event(self, event):
        if event["type"] != "message":
            return {"type": "noop"}

        command = parse_command(event["text"])
        self.state, action = transition(
            self.state,
            command["intent"],
            command.get("args"),
        )
        return action

    def execute(self, action):
        if action["type"] == "reply":
            print(action["text"])
            return

        if action["type"] == "shutdown":
            print("bot offline")
            self.running = False
            return

    def run(self):
        while self.running:
            event = self.poll_event()
            action = self.handle_event(event)
            self.execute(action)
```

这段代码看起来很朴素，但已经包含了 Bot 的四个核心骨架：

- 事件循环
- 结构化解析
- 状态驱动决策
- 执行动作

### 6. 为什么这种最小实现值得亲手写

因为只有当你从零搭过一次，才会真正理解很多高级框架在替你做什么：

- 为什么要把平台事件映射成统一对象
- 为什么对话流程经常写成状态机
- 为什么命令系统和 NLU 都在做“语义压缩”
- 为什么执行层总是最容易出副作用问题

很多人一开始就接入大型框架或 LLM，Bot 看起来“很快能跑”，但一旦出现上下文错乱、重复执行、状态漂移、权限误触发，就会发现自己并没有真正理解这个系统。

先写一个极简 Bot，就是先把黑箱拆掉。

## 四、进阶方向

当你的 Bot 不再满足于关键词匹配和静态规则后，系统复杂度会迅速上升。  
真正的进阶，不是“接更多 API”，而是让 Bot 从一个被动脚本，逐步演化为一个更强的上下文代理。 🌒

### 1. NLU 集成

NLU（Natural Language Understanding，自然语言理解）让 Bot 不再依赖严格命令格式，而能从自然表达里抽取意图与槽位。

例如：

```text
“帮我把 staging 部署到测试环境”
```

被解析为：

```json
{
  "intent": "deploy_service",
  "slots": {
    "service": "staging",
    "target_env": "test"
  }
}
```

这一步通常可以通过以下路径实现：

- 关键词和规则增强
- 文本分类模型
- 序列标注抽槽
- 检索 + 模板解析
- LLM function calling / tool calling

进阶的关键不是“用了 NLU 就更智能”，而是要控制错误语义进入执行层的概率。  
对高风险动作，宁可多一次确认，也不要让“看起来理解了”直接变成真实副作用。

### 2. 对话上下文管理

一旦 Bot 支持多轮对话，就必须回答几个更难的问题：

- 当前这句话是在延续哪个话题？
- 用户上一轮提供的参数是否仍然有效？
- 什么时候该清空上下文？
- 多个会话如何隔离？

上下文管理不是简单拼接历史消息。  
真正可用的上下文系统通常需要同时处理：

- 短期上下文：最近几轮消息
- 结构化记忆：用户设置、任务状态、偏好
- 长期记忆：历史事件摘要
- 安全边界：哪些上下文不能跨会话泄漏

如果没有上下文压缩和边界设计，Bot 很快就会出现典型问题：越聊越乱、记忆污染、响应漂移、token 成本失控。

### 3. 反检测机制

对于自动化 Bot 和爬虫 Bot，真正的难点往往不是功能实现，而是**如何在敌对环境中持续运行**。  
平台可能会根据访问频率、请求指纹、行为节奏、设备特征、鼠标轨迹、账号关系等信号识别 Bot。

因此，进阶系统往往需要考虑：

- 速率限制与随机抖动
- 指纹隔离
- 代理池与出口轮换
- 人机混合流程
- 浏览器自动化与真实渲染
- 失败回退与任务切片

这里要特别强调一点：反检测不是“隐身魔法”，而是与平台风控持续博弈的系统工程。  
任何过度激进的自动化策略，最终都会把 Bot 暴露成可识别模式。

### 4. LLM 驱动 Bot

这是近几年最有吸引力、也最容易被神化的方向。  
LLM 驱动 Bot 的本质，不是“把聊天模型包一层壳”，而是把大语言模型接入到 Bot 的认知链条中，让它参与：

- 意图理解
- 参数抽取
- 响应生成
- 工具选择
- 任务规划
- 结果总结

典型结构常常变成：

```text
[用户输入]
   -> [上下文拼装]
   -> [LLM 解析/规划]
   -> [工具调用]
   -> [结果汇总]
   -> [安全检查]
   -> [输出]
```

这种架构能显著提高 Bot 的表达能力与开放任务处理能力，但也会带来新的系统代价：

- 幻觉
- 指令注入
- 上下文污染
- 响应不稳定
- 成本不可控
- 延迟增大

因此，LLM 更适合放在“认知层”和“解释层”，而不是无约束地直接接管执行层。  
一句话概括：**让模型负责理解与建议，让程序负责边界与落地。**

### 5. 从 Bot 到 Agent 的边界

很多现代系统喜欢把 Bot 和 Agent 混用，但两者并不完全等价。

- Bot 更强调事件响应与任务执行
- Agent 更强调目标驱动、规划、自主迭代

如果你的系统已经开始出现下面这些特征：

- 能自主拆分任务
- 能反复调用工具修正结果
- 能维护中间工作记忆
- 能依据失败反馈改变策略

那它已经在向 Agent 形态靠近。  
但无论名字如何变化，基础仍然没有变：输入、状态、决策、执行、反馈。

## 五、推荐学习资源与经典开源项目

如果你想真正学会做 Bot，建议不要只看“某个平台 SDK 教程”。  
更高效的路径是同时观察三层内容：

- Bot 的通用架构
- 具体平台的事件模型
- 经典开源项目如何处理状态、扩展与安全边界

### 1. 推荐学习资源

#### 《Designing Data-Intensive Applications》

虽然这本书不是专门讲 Bot，但它非常适合理解事件流、状态一致性、消息处理、重试、幂等、队列与存储边界。  
很多中大型 Bot 的真实难点，本质上都落在这些系统问题上。

#### 《Game AI Pro》系列

如果你对游戏 AI Bot 感兴趣，这是一条非常强的延伸线。  
它能帮助你理解有限状态机、行为树、路径规划、效用决策等机制，看到“Bot 决策”在对话系统之外的另一条工程脉络。

#### 平台官方开发文档

无论你做 Telegram Bot、Discord Bot、Slack Bot、飞书 Bot、企业微信 Bot，官方事件模型文档都必须认真读。  
真正影响实现质量的，通常不是“如何发送一条消息”，而是：

- 事件签名怎么校验
- 重试语义是什么
- Webhook 有哪些时序约束
- 权限模型怎么设计
- 限流策略如何触发

#### 状态机与工作流建模资料

建议额外学习有限状态机、行为树、事件溯源、Saga、工作流编排等概念。  
Bot 一旦开始承担真实流程任务，这些知识会比“多会几个 SDK 方法”更有价值。

### 2. 经典开源项目

#### Hubot

GitHub 早期非常经典的聊天机器人框架。  
它展示了如何把命令路由、脚本插件、消息平台接入抽象成统一模型。即使今天不一定是最新选择，仍然很适合作为历史起点理解“Bot 框架”为何这样分层。

#### Errbot

Python 生态里知名的聊天 Bot 框架。  
它对插件、命令、后端适配的组织方式很有代表性，适合用来观察一个 Bot 如何逐步从脚本成长为可扩展系统。

#### Rasa

Rasa 是开源对话系统和 NLU 体系里的代表项目。  
它特别适合学习下面这些问题：

- 意图识别如何工程化
- 槽位填充如何落地
- 对话策略如何管理
- 规则与模型如何混合

如果你想从“命令式 Bot”进入“多轮对话 Bot”，Rasa 很值得拆解。

#### NoneBot

中文社区里非常活跃的 Python Bot 框架之一，尤其适合观察事件驱动、插件生态、适配器设计、异步处理方式。  
它也是理解“平台差异如何被框架层吸收”的好样本。

#### Botpress

如果你关心可视化工作流、会话设计器、企业对话系统，这类平台型开源项目值得研究。  
它体现的是另一种路径：把 Bot 从代码工程扩展成“可编排的产品系统”。

#### Microsoft Bot Framework

这是理解企业级对话 Bot 体系的一个重要参照物。  
即使不直接采用，也值得学习它对通道接入、会话状态、对话抽象和企业集成的处理思路。

### 3. 学习顺序建议

如果你是第一次认真做 Bot，我更建议按这个顺序推进：

1. 先自己写一个极简命令式 Bot，理解事件循环、解析、状态机。
2. 再接一个真实平台，体会 Webhook、鉴权、限流和失败重试。
3. 然后引入状态持久化，让 Bot 能跨轮次、跨进程记住东西。
4. 最后再考虑 NLU、LLM、工具调用与复杂编排。

顺序不能反。  
如果一开始就把系统建在最抽象、最昂贵、最不可控的认知层上，后面几乎一定会被调试成本反噬。

## 收束

> `SYSTEM NOTE`
>
> Bot 不是“会聊天的玩具”，而是一种可持续接入世界、解释信号、积累状态并施加动作的软件形态。  
> 你真正要构建的，不是一个会回复的函数，而是一台在不确定环境中仍能保持结构稳定的小型代理系统。 🌌

从 build-your-own-x 的学习语境看，自己做一个 Bot 的价值，不在于复刻某个流行平台，而在于亲手理解这件事的骨架：  
**输入如何被解释，状态如何被维护，决策如何被生成，动作如何被安全执行。**

当你把这条主线真正做通之后，聊天 Bot、自动化 Bot、游戏 AI Bot、爬虫 Bot，都会开始显出它们共享的底层结构。  
那时你写的不再只是一个“能跑的机器人”，而是一套可进化的 dark tech 代理原型。
