# Day 22 · Frontend Framework / Library

> `UI RUNTIME // STATE DRIVES VIEW`
>
> 前端框架表面上是在“写页面”，底层其实是在解决一个更硬核的问题：  
> 当状态不断变化时，如何以可维护、可预测、可扩展的方式，把抽象的数据持续投影成真实界面。

## 这是什么

前端框架 / 库，本质上是一层位于 **业务状态** 与 **浏览器渲染对象** 之间的运行时系统。它不只是帮你“少写 DOM 操作”，而是在重新定义 UI 的构建方式：

- 你不再手工描述“先创建哪个节点，再插入哪里”
- 你改为声明“当前状态下，界面应该长什么样”
- 框架负责决定：何时重新计算、比较哪些节点、怎样最小化真实更新、如何维持组件边界

如果从计算模型角度看，前端框架做的是一件关键的事：**把命令式 DOM 操作，提升为声明式状态到视图的映射**。

更严谨地说，一个现代前端框架通常同时包含以下几个核心子系统：

- 组件模型：把 UI 切成可组合、可复用、可封装的单元
- 渲染模型：把模板、JSX 或渲染函数转换成可比较的中间表示
- 更新模型：在状态变化后，决定哪些部分需要重新计算
- 协调模型：比较新旧树结构，生成最小更新集合
- 提交模型：把更新真正落到 DOM、事件、样式、属性和副作用上

所以，“框架”不是一套 API 的堆积，而是一台专门处理 UI 增量更新的解释器。

## 怎么使用

从使用者角度，前端框架最常见的工作流不是“操作页面”，而是“组织状态和依赖关系”。

一个典型流程如下：

```text
[用户输入 / 网络返回 / 定时器]
              |
              v
         [状态发生变化]
              |
              v
   [框架调度更新并重新执行渲染逻辑]
              |
              v
      [生成新的组件树 / VNode 树]
              |
              v
         [Diff / Reconcile]
              |
              v
        [最小化提交到真实 DOM]
```

实际使用时，通常会围绕四件事展开：

### 1. 用组件描述界面

组件不是“把 HTML 拆小块”这么简单。它的意义在于：把结构、行为、局部状态、依赖边界封装进一个稳定单元。  
一个组件应该对外暴露输入，对内维护实现细节。

### 2. 用状态驱动渲染

框架不是鼓励你“随时改 DOM”，而是鼓励你维护一份更高层的状态源。  
状态变了，视图自然重算；视图不该成为事实来源，而应是状态的投影结果。

### 3. 把副作用隔离出去

请求数据、订阅事件、读取滚动位置、操作焦点、启动动画，这些都不属于纯渲染逻辑。  
现代框架往往要求把它们放进明确的副作用机制中，否则渲染阶段会被污染，更新顺序会变得不可预测。

### 4. 管理数据流，而不是追逐页面问题

前端越复杂，越不能用“看到哪里错了就改哪里”的方式维护。  
更可靠的思路是：

- 谁拥有这份状态
- 谁只消费它
- 谁可以修改它
- 修改后哪些组件应当重新计算
- 是否需要异步缓存、派生值、回滚或时间旅行调试

框架的正确使用方式，不是熟记多少钩子，而是先把数据流设计清楚。

## 适用场景

前端框架最适合处理的是 **状态复杂、交互频繁、多人协作、长期演进** 的界面系统。

- 单页应用或局部高交互应用：页面不是一次性渲染后结束，而是持续响应用户、网络和本地状态变化
- 中后台与复杂表单系统：字段联动、权限控制、校验链路、异步回填很多，手写 DOM 很快失控
- 设计系统与组件库：需要稳定的封装边界、复用机制与一致的更新语义
- 实时界面：聊天、协作编辑、监控面板、交易面板等，更新频繁且需要精细控制重渲染成本
- 多渲染目标场景：同一套组件模型有机会映射到 DOM、Native、Canvas 或自定义宿主环境

它的核心价值，不是“做页面更快”，而是让 **复杂 UI 的变化过程可以被建模、约束和调试**。

## 不适用边界

前端框架并不是所有 Web 问题的默认答案。

- 纯静态页面或一次性活动页：如果几乎没有状态流转，引入完整框架往往只是增加构建和运行时负担
- 极小型脚本增强场景：只给现有页面补一个按钮、弹层、埋点时，原生 DOM 可能更直接
- 强实时绘制型应用：如果主渲染目标是 Canvas / WebGL，DOM 组件树可能不是主战场，框架只能做外围状态组织
- 超低运行时预算环境：框架的抽象层、调度器、响应式追踪、序列化和 hydration 成本不是免费的
- 需求高度短命且不可复用：当系统根本不会演进时，过重的组件架构可能得不偿失

真正应当避免的，不是“用框架”，而是 **把框架当成一切复杂度的自动消音器**。  
如果状态边界本身设计混乱，再先进的框架也只是在更优雅地放大混乱。

## 为什么重要

前端框架重要，不是因为它流行，而是因为现代 UI 的复杂度已经远超“操作几个 DOM 节点”的时代。

### 1. 它重新定义了 UI 编程模型

一旦你理解“界面 = 状态的函数”，很多看似零散的问题会被统一起来：

- 为什么不要到处直接改 DOM
- 为什么局部状态乱放会导致同步问题
- 为什么副作用必须与渲染分层
- 为什么列表稳定 `key` 会影响整个更新正确性

### 2. 它迫使你面对增量更新的本质

浏览器可以渲染页面，但浏览器并不知道你的业务状态语义。  
框架的存在，就是在应用层补出这一层语义：**哪些变化只是属性变了，哪些变化意味着组件应当卸载重建，哪些变化应该延后，哪些必须同步提交**。

### 3. 它是理解现代前端生态的底座

路由、状态库、表单库、动画库、SSR、Hydration、Server Components、Signals、编译优化，这些东西都不是孤立技术。  
它们建立在同一个问题之上：**状态如何跨越时间与组件边界，被正确传播和渲染**。

### 4. 它训练的是系统思维，不只是页面技巧

自己实现一个迷你框架时，你会第一次清楚地看到：

- 抽象层一旦上升，调试难度也会上升
- 性能问题很多时候不是“算得慢”，而是“更新范围过大”
- 正确性问题很多时候不是“逻辑错”，而是“依赖追踪错、生命周期错、调度时机错”

理解框架，本质上是在学习如何管理一个会持续演化的交互系统。

## 建议延伸

- 先做一个最小版渲染器：支持 `h(type, props, children)` 和递归挂载，先理解“UI 树如何落到 DOM”
- 再补虚拟 DOM 与 Diff：重点观察同层比较、节点复用、`key`、列表移动和卸载重建
- 自己实现一套响应式系统：从 `effect`、依赖收集、触发更新、`computed`、调度队列开始
- 尝试写一个简化状态库：实现 `store`、`subscribe`、`dispatch`、`reducer`，理解单向数据流
- 研究模板编译：把模板或 JSX 编译成渲染函数，理解运行时框架与编译时框架的分工
- 继续往深处看调度：批处理、优先级、可中断渲染、提交阶段、副作用清理
- 进阶到 SSR / Hydration：理解“服务器先输出 HTML，客户端再接管事件与状态”的成本和约束

一个很有价值的练习路径是：

```text
手写 DOM
  -> VNode
  -> Diff
  -> 组件实例
  -> 响应式依赖追踪
  -> 调度器
  -> 全局状态
  -> SSR / Hydration
```

走完这条路径后，框架对你来说就不再是黑盒，而会变成一组可以拆解、替换、优化的机制组合。

## 核心原理

前端框架真正难的地方，不在模板语法，而在它如何把“变化”变成“可控的增量更新”。下面这几个机制，是理解现代框架的主骨架。

### 1. 组件化：不是拆文件，而是建立边界

组件化首先解决的是 **局部封装问题**。  
没有组件时，页面往往是一团共享变量、共享 DOM 引用、共享事件回调的网状结构；随着功能增长，任何改动都可能影响整页。

组件的核心价值有三层：

- 结构边界：界面可以被组织成树，而不是一张无边界的事件网
- 数据边界：父传子、子发事件、上下文注入，本质上都在定义信息流路径
- 生命周期边界：挂载、更新、卸载都有明确语义，资源可以被准确申请与释放

组件树实际上就是应用的 **UI 拓扑图**。  
而一旦 UI 被表示成树，框架就有机会做两件事：

- 递归地描述界面
- 递归地比较变化

这就是后续虚拟 DOM 和 diff 能成立的基础。

### 2. 虚拟 DOM：把“界面”变成可计算对象

真实 DOM 的问题不在于“不能用”，而在于它太具体、太昂贵、太贴近浏览器实现。  
框架因此会先把界面描述成一层更轻的中间表示，通常称为 VNode / Virtual DOM。

一个 VNode 往往包含：

- 节点类型：原生标签、文本节点或组件类型
- 属性集合：class、style、事件、普通属性
- 子节点列表
- 可选标识：`key`

这样一来，渲染函数的输出就不再是“直接改页面”，而是“返回一棵描述页面的对象树”。

```text
state -> render() -> virtual tree -> diff -> patch -> real DOM
```

虚拟 DOM 的真正意义，不是“比真实 DOM 快”，而是：

- 它提供了可比较的数据结构
- 它把渲染逻辑和宿主环境操作解耦
- 它允许框架先算出差异，再决定如何提交

需要注意的是，**虚拟 DOM 不是前端框架的唯一答案**。  
像 Svelte 更偏编译期优化，Solid 更偏细粒度响应式更新，它们都在尝试绕开“整棵子树重跑再 diff”的成本。  
因此更准确的结论是：虚拟 DOM 是一类重要方案，而不是唯一正统。

### 3. Diff 算法：在正确性与复杂度之间做工程折中

如果要比较两棵任意树并求最优编辑路径，理论复杂度会非常高，直接用于 UI 更新不可接受。  
现代前端框架普遍采用启发式策略，把问题简化到“足够正确且足够快”。

常见假设包括：

- 不同类型的节点通常代表不同子树，应直接替换
- 同层节点的相对稳定性高于跨层重排
- 开发者可以用 `key` 提供身份信息，帮助框架识别节点复用关系

因此，典型 diff 过程大致是：

### 3.1 节点类型比较

- 旧节点和新节点类型不同：直接卸载旧节点并挂载新节点
- 类型相同：尝试复用 DOM 实例，只更新属性与子节点

这一步决定了“保留还是重建”。  
一旦判断错误，就会出现状态错位、输入框光标跳动、组件实例意外复用等问题。

### 3.2 属性比较

对同一节点，框架会计算旧属性和新属性的差异：

- 新增哪些属性
- 删除哪些属性
- 哪些属性值发生变化
- 哪些事件处理器需要替换

这里看似简单，实际很容易踩坑，因为 DOM 属性、HTML attribute、布尔属性、样式对象、事件绑定策略并不完全一致。

### 3.3 子节点比较

最关键的复杂度通常在列表更新。  
如果没有 `key`，框架只能按位置猜测身份，结果是头部插入一个元素，后面整个列表都可能被错误地视为“逐个修改”。

`key` 的作用不是“消除警告”，而是告诉框架：

- 这个节点的身份是什么
- 它是移动了、复用了，还是应该被销毁

常见列表 diff 优化包括：

- 头尾双指针比较：快速跳过前后相同片段
- 基于 `key` 的索引表：把查找成本降下来
- 最长递增子序列（LIS）：在保留相对顺序的前提下，减少真实移动次数

这说明 diff 算法从来不是“聪明猜测全部最优解”，而是基于 UI 常见模式做成本受控的启发式优化。

### 4. 响应式系统：找到“谁依赖了谁”

虚拟 DOM 解决的是“变更如何提交”，响应式系统解决的是“什么时候应该重新算”。

最朴素的方法是状态变了就整页重渲染，但这会造成大量无意义计算。  
于是框架开始引入依赖追踪：当某段渲染逻辑读取了某个状态，就记录这种依赖；当状态未来变化时，只通知真正依赖它的计算单元。

一个典型响应式系统包含四个核心件：

- `track`：读取时收集依赖
- `trigger`：写入时触发依赖
- `effect`：包裹会响应更新的计算逻辑
- `scheduler`：决定立即执行、批处理执行还是延后执行

最常见的两类实现路径是：

### 4.1 基于 getter / setter 或 Proxy 的追踪

当代码读取 `state.count` 时，框架在 `get` 阶段记录“当前 effect 依赖了 count”；  
当代码写入 `state.count = 2` 时，框架在 `set` 阶段找到相关 effect 并重新调度。

这类机制的关键难点不是“能不能触发更新”，而是：

- 嵌套 effect 如何正确建立依赖栈
- 条件分支变化后，旧依赖如何清理
- 避免同一轮更新重复触发
- 计算属性如何缓存且保持脏标记正确

### 4.2 基于显式 Signal 的追踪

另一类框架会把响应式值设计成显式容器，例如 `count()` 读取、`setCount()` 写入。  
这种方式的优点是依赖关系更清晰，更容易做细粒度更新；代价是编程模型通常更显式，也更要求开发者理解依赖图。

从本质上说，响应式系统在维护一张 **运行时依赖图**。  
框架的性能上限，很大程度上取决于这张图是否足够精确，能否避免“变化一点，重跑一片”。

### 5. 状态管理：让变化可追踪，而不是到处蔓延

UI 复杂到一定程度后，问题已经不是“有没有状态”，而是“状态放哪里、怎么流动、谁能改它”。

状态通常可以分成几层：

- 局部状态：只影响某个组件，如输入框值、展开收起
- 共享状态：多个组件共同依赖，如用户信息、主题、权限
- 派生状态：由其他状态计算得到，如过滤结果、统计摘要
- 远程状态：来自服务端，如请求结果、缓存、分页游标

状态管理的核心，不是创建一个全局仓库，而是保证三件事：

- 单一真实来源：同一份业务事实不要在多个地方重复维护
- 更新路径明确：谁能改、怎么改、改完通知谁，都要清楚
- 读写分离适度：读取尽量自由，写入尽量收敛

常见的两种思想路径：

### 5.1 单向数据流

以 Redux 一类模型为代表，更新过程通常是：

```text
view -> dispatch(action) -> reducer -> new state -> re-render
```

优点是：

- 状态变化路径稳定
- 可记录、可回放、可调试
- 不容易出现隐式双向联动

代价是：

- 样板代码可能较多
- 高频细粒度交互时，更新路径显得偏重

### 5.2 响应式共享状态

另一类方案更偏“谁依赖谁就自动更新”，共享状态可以直接被多个组件消费。  
优点是写起来更自然，局部更新更细；问题在于如果边界不清楚，状态传播会变得隐式，调试复杂度会上升。

所以状态管理的本质不是选 Redux 还是 Store，而是决定：

- 你的系统更需要严格可追踪性，还是更低心智负担
- 你的变化更像事务流，还是更像信号传播

### 6. 调度与批处理：不是一改就立刻重画

如果每次状态变化都立刻同步更新 DOM，系统会非常低效。  
框架通常会把同一事件循环中的多次变更合并，再批量执行渲染和提交。

调度器存在的原因包括：

- 合并重复更新，避免无意义重算
- 控制副作用执行时机
- 保证父子组件更新顺序
- 为高优先级任务让路，例如输入响应

更先进的实现还会区分：

- 渲染阶段：纯计算，可中断、可重试
- 提交阶段：真正操作宿主环境，必须保持一致性

这背后对应的是一个很重要的现实：  
**UI 更新不是单纯的函数调用问题，而是与事件循环、浏览器绘制、任务优先级绑定的调度问题。**

### 7. 编译优化：把运行时负担前移

并不是所有框架都愿意在浏览器里做大量运行时判断。  
一些框架会在构建阶段提前分析模板，生成更高效的更新代码。

编译期可以做的事包括：

- 标记静态节点，跳过重复比较
- 分析动态绑定位置，只更新真正变化的片段
- 内联事件与属性更新逻辑
- 把模板编译成更直接的 DOM 操作或更精确的渲染函数

这说明现代框架的竞争，已经不仅是 API 设计，而是 **运行时通用性** 与 **编译期可知性** 的权衡。

### 8. 一个关键认知：框架的核心任务不是“渲染”，而是“管理变化”

真正难的不是首屏把页面画出来，而是第二次、第三次、第一千次变化到来时，系统是否仍然：

- 更新正确
- 更新足够少
