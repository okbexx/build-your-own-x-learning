# Day 10 · BitTorrent Client

## build-your-own-x 对应原始项目地址

https://github.com/codecrafters-io/build-your-own-x#build-your-own-bittorrent-client

## 这是什么

BitTorrent Client 指的是一个能够参与 BitTorrent 协议网络的下载端程序。它的目标不是从一台中心服务器顺序拉取整个文件，而是先拿到一个 `.torrent` 元数据文件或 magnet 信息，再去发现其他节点，按片段从多个 peer 并行交换数据，最终在本地组装成完整文件。

自己实现 BitTorrent Client，重点不在“做出一个能下载电影的工具”，而在于真正吃透一种典型的分布式文件传输协议。这个题目会把很多抽象概念变成具体工程问题，比如：

- 元数据如何编码与解析
- 文件为什么要切成 piece
- peer 之间怎么握手、声明能力、交换可下载片段
- 为什么必须做哈希校验
- 多节点并发下载时如何保证正确性与吞吐量

如果你把它做完，得到的不只是一个小型客户端，更是一套对“分片传输、校验、一致性、对等网络、带宽调度”这些基础能力的直观理解。

## 怎么使用

这一天更适合作为“边读协议边落地实现”的练习。最有效的方式不是先追求完整客户端，而是按里程碑逐步做通。

推荐按下面顺序推进：

1. 先实现 bencode 解析器与编码器。BitTorrent 的 torrent 元数据通常使用 bencode 表示，整数、字符串、列表、字典都需要正确处理。
2. 读取 `.torrent` 文件，提取 `announce`、`info`、`piece length`、`pieces`、文件名与文件长度等关键字段。
3. 基于 `info` 字典计算 `info_hash`。这是后续向 tracker 报告、向 peer 握手时最关键的身份值之一。
4. 与 tracker 通信，拿到 peer 列表。先做最基础的 HTTP tracker 即可，不必一开始就上 UDP tracker。
5. 与单个 peer 建立 TCP 连接，完成 handshake，理解 peer id、保留位、info hash 的作用。
6. 处理核心消息流：`bitfield`、`interested`、`unchoke`、`request`、`piece`。先从“能下载单个 piece”做起。
7. 增加 piece 校验、失败重试、并发下载、磁盘写入与断点恢复，逐渐把原型推进到可用状态。

实践时可以给自己设一组明确验收标准：

- 能打印 torrent 元数据
- 能连接 tracker 并列出 peers
- 能连上一个 peer 并完成握手
- 能请求并接收一个 piece 的 block
- 能校验 piece 的 SHA-1
- 能把所有 piece 组装成完整文件

如果你是第一次接触该协议，不要一上来就做“完整下载器 + 图形界面 + 磁力链接 + DHT”。先做最小闭环：`.torrent` 解析 -> tracker -> peer -> piece 下载 -> 哈希校验。这条路径最能建立正确的协议直觉。

## 核心原理

BitTorrent 的核心思想是“把大文件拆成小块，让下载者同时也是上传者”。这使得系统的带宽来源不再只依赖单点服务器，而是随着参与节点增多而扩展。

第一层原理是元数据驱动。`.torrent` 文件不会直接包含文件内容，而是描述：

- 文件结构
- 每个 piece 的长度
- 所有 piece 的哈希摘要
- tracker 地址

客户端拿到这些信息后，才能知道“总共有多少块、每块应当多大、下载回来后怎么验证”。

第二层原理是基于 piece 的交换。一个文件会被切成多个 piece，每个 piece 又可能进一步拆成更小的 block 进行请求。这样做有三个直接好处：

- 可以并行从多个 peer 下载不同 piece
- 某个 peer 掉线时，不会导致整个文件重下
- 客户端拿到部分 piece 后就能开始向别人上传，形成共享网络

第三层原理是校验优先。BitTorrent 默认假设网络中的数据并不天然可信，所以每个 piece 下载完成后，都要用元数据中的 SHA-1 摘要做校验。校验失败就丢弃重下，而不是把错误内容写进最终文件。这个机制是协议可靠性的底座。

第四层原理是状态协商。peer 之间不是连上就直接发数据，而是先通过一系列消息同步状态：

- `handshake` 用来确认双方在同一个 torrent 上通信
- `bitfield` 告诉对方自己拥有哪些 piece
- `interested` 表示“我想要你手上的数据”
- `choke/unchoke` 控制是否允许请求数据
- `request/piece` 完成实际的数据请求与返回

这里最值得理解的是：协议并不是“请求一个文件”，而是“在一组状态机规则中，持续请求若干 block，并逐步完成整个 piece 集合”。一旦你能把它想成状态机和消息流，代码结构就会清晰很多。

第五层原理是调度。真实客户端性能好坏，往往不取决于“会不会下载”，而取决于“如何挑选 piece、如何分配请求、如何控制并发”。常见策略包括：

- 优先下载稀缺 piece，降低全网稀有块丢失风险
- 对慢 peer 少分配请求，对稳定 peer 多分配请求
- 管理 in-flight requests，避免连接空转
- 维持上传，提升在网络中的交换价值

这部分说明 BitTorrent 不只是协议解析题，它同时也是一个调度与系统设计题。

## 适用场景

BitTorrent Client 适合用来理解以下场景：

- 大文件分发：例如镜像、归档数据、安装包等，文件大、下载人数多、单点带宽容易成为瓶颈。
- 去中心化传输：不希望把所有下载压力压在一台源站上，而是让参与者共同承担带宽成本。
- 断续网络环境：分片下载与校验机制使得中断恢复更自然，不必总是从头开始。
- 协议学习与系统训练：它非常适合训练网络编程、二进制协议、并发调度、校验与容错思维。

对学习者来说，这个题目尤其适合拿来练下面几类能力：

- TCP 长连接与消息边界处理
- 二进制数据解析
- 哈希与数据完整性验证
- 多连接并发模型
- 磁盘写入与随机访问

## 不适用边界

BitTorrent 不是所有文件传输问题的通用答案，下面这些边界要看清楚。

第一，它不适合强实时传输。BitTorrent 的设计目标是高效分发大体量静态内容，不是低延迟音视频会议，也不是毫秒级响应的数据同步。

第二，它不适合高保密、强权限控制场景。协议本身重点是分发效率，不是细粒度鉴权、审计、端到端业务安全。若业务要求严格访问控制，通常需要在更高层补足机制，甚至直接换方案。

第三，它不适合小而短的传输任务。对于几 MB 以内、一次性下载、参与者很少的内容，引入 torrent、tracker、peer 管理的复杂度往往得不偿失。

第四，它不适合你当前目标只是“学 HTTP 下载”。如果你还没有掌握基础 socket、协议报文、线程或异步模型，直接做完整 BitTorrent Client 会有点陡。更合理的路径是先补齐网络编程基础，再来做这个项目。

## 为什么它重要

这个主题的重要性在于，它把许多分散的系统概念压缩进一个可落地项目里。

从网络角度看，你会第一次真正面对“应用层协议如何建立在 TCP 之上”。你不再只是调用一个现成 SDK，而是自己处理连接、超时、消息格式、状态切换和错误恢复。

从分布式角度看，你会理解为什么“把资源切片”能提升系统弹性。很多现代系统本质上都在做类似的事：分块、复制、校验、重试、调度。对象存储、CDN、数据同步、任务分发，底层思想并不陌生。

从工程角度看，它会迫使你写出更像样的程序结构。一个能工作的客户端通常至少要有这些模块：

- 元数据解析
- tracker 通信
- peer 连接管理
- piece 调度
- 校验与存储

这意味着你不能把所有逻辑塞进一个脚本里。你必须开始考虑模块边界、状态表示、错误传播和测试方式。这正是从“会写代码”走向“会做系统”的转折点。

## 建议延伸

做完最小版本后，建议继续往下扩展，但顺序要克制。

优先级最高的延伸：

1. 加入 piece picker 策略，例如 rarest-first，观察吞吐与完成时间的变化。
2. 做断点续传，把已完成 piece 状态持久化，下次启动时只补缺失块。
3. 支持多文件 torrent，正确处理文件偏移与分段写盘。
4. 为 peer 管理加上超时、黑名单与失败重试，提升稳定性。

第二阶段可以挑战：

1. 支持 magnet link，理解从磁力链接到元数据发现的流程。
2. 研究 DHT 与 PEX，理解在弱中心化条件下如何发现更多 peers。
3. 增加上传逻辑与限速策略，真正成为完整的 swarm 成员。
4. 为客户端写集成测试，用本地 mock tracker 和 mock peer 验证协议行为。

如果你的目标是“把这个项目学到能迁移”，不要只停留在下载成功。更好的问题是：

- 为什么 piece 长度会影响吞吐和管理成本
- 为什么 block 请求窗口会影响链路利用率
- 为什么坏数据必须以 piece 为单位校验
- 为什么 peer 多不一定更快，调度策略反而更关键

当你能回答这些问题时，这一天的价值才真正落地。
