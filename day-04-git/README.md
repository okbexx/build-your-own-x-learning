# Day 4 · Git

## build-your-own-x 对应原始项目地址

- [Git](https://github.com/codecrafters-io/build-your-own-x#build-your-own-git)

## 这是什么

Git 是一个分布式版本控制系统，但如果只把它理解成“保存代码历史”，通常会越学越乱。更准确的说法是：**Git 是一个用内容寻址对象、引用指针和提交图来记录项目演化过程的快照系统**。

“自己动手实现 Git / 理解 Git 核心机制”的学习价值，不在于重新造一个完整的 `git` 命令，而在于亲手拆开这些最关键的问题：

- 文件内容为什么会变成 blob 对象
- 目录结构为什么会变成 tree 对象
- 提交为什么本质上是指向 tree 和父提交的 commit 对象
- 分支为什么只是一个可移动的引用
- 暂存区为什么存在，且它到底解决了什么问题

当这些机制串起来以后，`add`、`commit`、`branch`、`checkout`、`merge` 就不再是零散命令，而是一套一致的底层模型。

## 怎么使用

从学习者视角，理解 Git 最好的方式不是先背命令，而是按内部流程去观察一次最小工作流：

1. 在工作区修改文件。
2. 用 `git add` 把工作区内容写入暂存区。
3. 用 `git commit` 基于暂存区生成一次新的快照提交。
4. 让分支引用移动到这个新提交。
5. 用 `git log --graph --oneline --decorate` 观察提交图结构。

如果你是“自己实现 Git”，通常会先实现这样一条最小链路：

1. `init`：创建 `.git` 目录和必要元数据。
2. `hash-object`：把文件内容写成对象。
3. `write-tree`：把目录结构组织成 tree。
4. `commit-tree`：创建 commit 对象。
5. `update-ref`：移动分支或 HEAD 引用。

这条链路足以帮你看清：Git 的核心不是 CLI 语法，而是**对象存储 + 引用更新**。

## 核心原理

### 1. 内容寻址：对象名来自内容，而不是来自文件名

Git 最重要的设计之一，是把对象的标识建立在内容摘要上。一个对象写入对象库后，会得到一个由其内容计算出来的 ID。

这带来几个直接结果：

- 相同内容天然可复用
- 对象天然具有不可变特征
- 历史记录可以稳定引用过去状态

也就是说，Git 存的不是“某个文件第 3 版”，而是“某份内容对应的对象”。

### 2. 三种核心对象：blob、tree、commit

理解 Git，先不要急着看命令，先看对象模型：

- **blob**：保存文件内容本身，不关心文件名。
- **tree**：保存目录结构，把名字、权限和子对象关联起来。
- **commit**：保存一次项目快照的入口，并记录作者、说明、父提交等信息。

一个 commit 并不直接保存所有文件文本，它主要是指向某棵 tree，再由 tree 层层指向 blob。于是，一次提交其实是在说：**“项目在这个时刻的完整目录快照是这棵树。”**

### 3. 暂存区：把“编辑中的状态”和“准备提交的状态”分开

很多初学者最困惑的是 `git add`。根本原因在于他们没有把 Git 看成三层状态：

- 工作区：你当前正在编辑的文件
- 暂存区：你准备提交的快照候选集
- 仓库历史：已经提交完成的对象与引用

暂存区的意义在于，它允许你从一堆修改中，挑出一部分先构成下一次提交。这不是多余设计，而是 Git 能够精细组织提交历史的关键。

### 4. 引用系统：分支不是“提交集合”，而是一个指针

Git 分支本质上只是一个引用，里面记录“当前分支指向哪个 commit”。当你产生新提交时，分支只需要移动到新的 commit 上。

这意味着：

- 创建分支非常轻量
- 切换分支本质上是在切换引用目标
- HEAD 用来表示“你当前站在哪个引用或提交上”

当你真正理解“branch = ref”，很多 Git 行为会一下子变得非常清晰。

### 5. 提交图：版本历史不是线性列表，而是有向无环图

每个 commit 都可以指向一个或多个父提交，因此整个历史天然形成 DAG（有向无环图）。

这就是为什么 Git 能表达：

- 线性开发
- 分支分叉
- 合并提交
- 历史回溯

所以 merge 并不是“把两份代码文本强行拼起来”，而是**在提交图上寻找共同祖先，并构造新的图节点**。

### 6. 差异只是视图，快照才是底层事实

用户平时看到的是 diff，于是容易误以为 Git 在底层保存的是一连串补丁。对学习者来说，一个关键纠偏是：**Git 的核心心智模型更接近快照，而不是补丁流。**

diff 很重要，但它更像是为了展示、比较和合并而计算出来的视图；真正稳定的底层表达仍然是对象与快照引用。

## 适用场景

- 学习版本控制系统的基础设计
- 理解代码托管平台为何能高效管理分支与 PR
- 学习内容寻址存储、不可变对象与引用更新
- 为实现简化版 VCS、备份系统、对象数据库打基础
- 帮助团队成员建立正确的 Git 心智模型，减少“命令会背但经常用乱”的情况

## 不适用边界

- 如果目标只是背几个常用命令快速提交代码，深入实现 Git 会显得过重
- 如果你关心的是协作文档产品体验，Git 的模型并不直接等于实时协同编辑模型
- 如果你需要处理数据库事务、二进制大文件或多主同步冲突，原生 Git 不是通用解决方案
- 如果你期望一次学习就覆盖 rebase、bisect、packfile、gc、protocol 等全部细节，最小实现并不够

换句话说，自己实现 Git 很适合建立核心认知，但它不是对所有版本管理问题的一次性总解答。

## 为什么重要

Git 是现代软件开发的地基之一，但很多人长期停留在“会敲命令，不懂状态”的层面。这样一来，一旦遇到分支切换、冲突、回滚、rebase 或 detached HEAD，就会开始依赖记忆和试错。

而“自己动手实现 Git / 理解 Git 核心机制”之所以重要，是因为它能把常见困惑统一成一个模型：

1. **版本历史为什么可信**：因为对象不可变、引用可追踪。
2. **分支为什么便宜**：因为它只是移动引用，不是复制整个仓库。
3. **提交为什么要小而清晰**：因为提交本质上是在组织快照演化图。
4. **很多危险操作为什么危险**：因为它们本质上是在改写引用关系，而不只是“改一下显示结果”。

一旦你真正理解这些，再看 Git 命令，会发现它们多数只是对对象和引用做读写操作的不同入口。

## 建议延伸

- 先实现一个最小 Git：支持 `init`、`hash-object`、`cat-file`、`write-tree`、`commit-tree`。
- 再补上 `add` 与 index 机制，专门理解暂存区为什么存在。
- 用 `git cat-file -p`、`git ls-tree`、`git rev-parse` 直接观察真实仓库对象，不要只停留在高层命令。
- 延伸研究 packfile、delta compression、reflog、rebase、merge-base，理解 Git 在大型仓库中的效率来源。
- 如果想更进一步，可以把 Git 与数据库 WAL、内容寻址存储、Merkle DAG 放在一起比较，建立更通用的系统设计视角。
