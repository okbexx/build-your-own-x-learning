# Day 16 · Programming Language

## build-your-own-x 对应原始项目地址
- [Programming Language](https://github.com/codecrafters-io/build-your-own-x#build-your-own-programming-language)

## 这是什么
从零实现一门编程语言，不是“设计几条语法规则”这么简单，而是亲手搭一条把文本程序变成可执行语义的完整管线。你需要定义字符如何切分成 token，token 如何组成语法结构，语法结构如何承载语义，语义又如何落到解释执行、字节码虚拟机、JIT 或原生机器码。这个主题的核心不是做一个玩具 REPL，而是建立一套精确模型：什么叫表达式、什么叫作用域、变量绑定在什么时候确定、对象何时分配和释放、异常和控制流如何传播、类型系统在什么时候介入。

它通常覆盖几个关键层次：词法分析器负责把线性字符流离散化；语法分析器负责把 token 组织成 AST 或更底层 IR；语义分析阶段负责名称解析、类型检查、闭包捕获、可达性与约束验证；执行层负责解释器、栈机、寄存器 VM 或代码生成；运行时则承担内存管理、垃圾回收、对象模型、模块系统、FFI、异常机制等职责。只要你真的把这些层串起来，就会发现“语言”本质上是一个小型操作系统加编译工具链的交叉体。

## 怎么使用
最有效的用法不是一次性追求“做出一门语言”，而是按抽象边界逐层推进，每一层都要求可观测、可调试、可替换。

1. 先固定一个极小语言核：字面量、变量、二元运算、条件、函数调用。不要一开始就引入类、宏、泛型。
2. 实现 lexer，并确保它不仅能产出 token，还能保留位置信息。后续的报错质量，取决于你现在是否记录了行列号、文件偏移和词法上下文。
3. 实现 parser，优先掌握递归下降或 Pratt parser。前者适合理解语法结构，后者尤其适合表达式优先级和结合性处理。
4. 构建 AST，并把“语法长得像什么”和“执行时意味着什么”分开。AST 不是结果展示层，而是后续静态分析和执行的语义载体。
5. 增加语义分析：符号表、作用域链、自由变量捕获、类型约束、返回路径检查。很多初学者跳过这一层，最后解释器和编译器会被一堆隐式规则污染。
6. 选择执行策略：先写 AST-walk interpreter 最容易验证语义；当性能和控制流复杂度上升，再引入 bytecode 和 VM。
7. 最后扩展运行时：内存分配、GC、对象布局、模块加载、标准库边界。这里决定语言是否能从“演示品”走向“可持续使用”。

如果你拿 build-your-own-x 作为学习入口，正确姿势是对照不同项目的实现路线，看它们在 parser、IR、类型系统、VM 设计上的取舍，而不是只复制语法外观。真正应该比较的是：为什么某项目选择字节码而不是 AST 解释，为什么某语言先做语义约束再生成 IR，为什么错误恢复放在 parser 层而不是 runtime 层。

## 核心原理
编程语言实现的难点，本质上是把“用户写下的表面结构”稳定映射成“机器可维护的内部表示”。

第一层原理是语法与语义分离。词法和语法只回答“这段文本长得合法吗”，并不回答“它是否有意义”。例如 `foo(bar)` 在 parser 看来只是调用表达式，但在语义层才知道 `foo` 是否已定义、是否可调用、参数个数是否匹配。这种分层避免把上下文依赖逻辑硬塞进 parser，降低系统耦合。

第二层原理是中间表示。AST 适合表达源语言结构，但不一定适合优化和执行；因此很多实现会把 AST lowering 到更规范的 IR，例如 SSA、三地址码或自定义 bytecode。IR 的价值在于把“复杂语法糖”压平成少量核心操作，使控制流、数据流和优化规则更容易表达。你写 `for`、`match`、闭包时觉得是高级结构，编译器往往会把它们降解为跳转、块、环境对象和调用约定。

第三层原理是绑定与作用域。变量名不是值，名称解析才把标识符映射到某个定义点。静态作用域意味着绑定关系由程序文本决定，不由运行栈偶然决定；闭包意味着函数离开定义环境后仍要携带自由变量引用。这里会牵扯栈分配、逃逸分析、环境链和 upvalue 捕获等问题。很多语言实现的复杂度，不在表达式求值，而在“这个名字到底指向谁”。

第四层原理是执行模型。解释器最直观，但每次执行都在走树或解码指令；编译器可以把开销前移到生成阶段，用更高吞吐换更复杂的实现。字节码 VM 是常见折中：先把高级结构编译成紧凑指令，再通过栈机或寄存器机执行。栈机实现简单，表达式求值自然；寄存器机指令更显式，通常有更低调度开销。JIT 再进一步，根据热点路径把动态信息反馈回代码生成。

第五层原理是运行时语义。只要语言支持字符串、对象、闭包、异常、并发或垃圾回收，运行时就不再是“附属模块”，而是语义的一部分。比如尾调用优化会影响递归是否栈溢出；GC 策略会影响暂停时间和对象可达性；对象模型会影响方法分派、继承布局和反射能力。语言规范里看起来抽象的一句话，往往意味着 runtime 内部一整套数据结构与协议。

第六层原理是错误模型。好的语言实现不只是“跑对程序”，还要“精确解释错误”。这要求每一层都保留来源信息，并在错误恢复上有策略：lexer 要指出非法字符，parser 要尽量同步到下一个可继续解析的位置，语义分析要给出定义链与期望类型，runtime 要能打印调用栈。工程上，诊断系统的设计质量常常决定这门语言是否真的可学、可调试、可维护。

## 适用场景
从零实现编程语言，最适合以下几类目标：

- 学习编译原理时需要把书本里的 CFG、symbol table、type inference、IR、GC 变成具体代码，否则概念很容易停留在术语层。
- 需要为特定领域构建 DSL，例如规则引擎、查询语言、模板语言、配置语言、数据变换管线。自己做语言，能把领域约束前置到语法和类型层，而不是散落在业务代码里。
- 需要理解现有语言的性能与语义边界。写过解释器或 VM 后，才真正知道动态分派、装箱拆箱、闭包捕获、异常展开为什么会贵，优化器为什么难写。
- 需要构建源码工具链。即使最终不发布新语言，实现 parser、AST 和语义模型也能直接服务于 linter、formatter、refactor、static analysis、language server。

## 不适用边界
这个方向不适合把“造语言”当成对业务复杂度的逃避。很多问题真正需要的是库、规则配置或更清晰的 API，不需要引入新语法和新运行时。

- 如果你的需求只是少量可配置逻辑，先考虑 JSON/YAML + 校验器，或嵌入现有脚本语言。语言实现的长期维护成本极高。
- 如果团队没有能力维护解析器、诊断系统、版本兼容和运行时，DSL 很容易在一年后变成没人敢改的遗留系统。
- 如果目标是立即获得性能收益，从零做语言通常不是捷径。你先要付出 parser、IR、runtime、tooling 的巨大成本，性能优化还只是后半程。
- 如果你无法明确语义边界，例如异常传播、空值规则、可变性、并发模型、模块隔离，那么越早实现，后期越难兼容演化。

真正的边界判断标准很简单：你是否需要一个新的“语义层”，而不只是新的“配置格式”。前者值得做语言，后者通常不值得。

## 为什么它重要
实现一门语言，是理解软件系统抽象成本最直接的方式之一。平时我们写业务代码，大量语义都被宿主语言替我们兜底；一旦自己实现语言，所有默认机制都会显形：表达式求值顺序是不是左到右，整数溢出如何定义，名字查找是词法还是动态作用域，函数是一等值后环境如何保存，错误发生时堆栈如何还原。你会第一次清楚看到，“高级语言的优雅”其实建立在一层层非常刚性的底层约束之上。

它的重要性还在于，它把多个传统上分散的知识域强制揉到一起：离散数学里的形式语言，系统里的内存与调用约定，软件工程里的模块化与测试，可观测性里的诊断与错误恢复，性能工程里的热点识别与优化策略。很少有别的练习，能同时训练抽象能力、系统能力和工程纪律。

对工程师来说，哪怕你永远不发布自己的语言，只要认真做过一次最小可用实现，你看待 Python、Go、Rust、JavaScript、JVM、LLVM 的方式都会变。你不再把语法当表面设计，而会自然追问它背后的 IR、runtime 和 trade-off。

## 建议延伸
建议把学习从“做出能跑的解释器”推进到“做出能解释自己设计选择的实现”。

- 先完成一个带函数、闭包、块作用域和错误定位的最小解释器，再尝试把 AST 执行改造成 bytecode VM，比较两种执行模型的复杂度与性能差异。
- 为语言补上语义分析层，而不是把所有检查推迟到运行时。亲自实现符号表、作用域解析、简单类型系统或约束检查，理解静态信息如何降低运行时复杂度。
- 选一个专题深入：GC、类型推断、模式匹配、宏系统、模块系统、协程、JIT。不要横向浅尝，单点打深更能建立判断力。
- 阅读成熟实现的源码时，重点看它们如何处理“边角但关键”的问题：错误恢复、增量解析、调试信息、标准库边界、宿主平台交互，而不是只看 parser 主流程。
- 如果你已经会基础编译原理，下一步可以把注意力放到 LLVM、Cranelift、WASM、SSA、escape analysis、inline cache 这些更贴近工业实现的话题上。

这类项目最有价值的产出，不是语言本身，而是你建立了一套可迁移的思维框架：如何把语法问题、语义问题、表示问题、执行问题和工程问题分层处理，并在每一层做明确取舍。
