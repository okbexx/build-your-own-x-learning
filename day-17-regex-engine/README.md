# Day 17 · Regex Engine

> 🌑 一台正则引擎，本质上不是“会匹配字符串的黑盒”，而是一套把**模式语言**编译成**状态机**，再在输入文本上执行的微型计算系统。  
> `pattern -> parse -> automaton -> match trace -> result`

## build-your-own-x 对应原始项目地址 → [Regex Engine](https://github.com/codecrafters-io/build-your-own-x#build-your-own-regex-engine)

## 这是什么

`Regex Engine` 指的是“正则表达式执行器”。它接收一段模式，例如 `a(b|c)*d`，再判断某段文本是否命中、命中的范围在哪里、捕获组里提取到了什么。

从工程视角看，正则引擎通常拆成三层：

1. **模式语法层**：定义 `.`、`*`、`+`、`?`、`|`、`()`、`[]`、`^`、`$` 等符号的含义。
2. **中间表示层**：把正则字符串解析成 AST、字节码或 NFA/DFA 图。
3. **执行层**：在输入文本上运行自动机，返回 `match / no match / captures`。

它与“字符串查找”最大的区别在于：字符串查找匹配的是**固定字面量**，正则引擎匹配的是**一类字符串的描述规则**。这意味着它处理的不是单一答案，而是一个语言识别问题。

## 怎么使用

⚙️ 学习这个主题时，不要把“怎么写正则”当重点，而要把“引擎如何理解正则”当重点。一个高效的实践顺序如下：

1. 先只支持**字面量匹配**，例如模式 `abc` 只匹配 `abc`。
2. 再加入**连接**与**通配符**，理解“状态按字符推进”的基本机制。
3. 增加 `|`、`*`、`+`、`?` 与 `()`，开始进入真正的自动机构造。
4. 最后实现 `^`、`$`、字符类、转义、捕获组，并处理错误输入。

可以用这组测试逐步逼近：

```text
Pattern: abc      Input: xxabcxx      => 命中 "abc"
Pattern: a.c      Input: abc          => 命中
Pattern: ab*      Input: abbbb        => 命中
Pattern: a|bc     Input: bc           => 命中
Pattern: ^ab+$    Input: abbb         => 全串命中
Pattern: (ab)+c   Input: ababc        => 命中，且可观察分组边界
```

如果你在做“从零实现”：

- 先决定语义模型：是做**回溯型引擎**，还是做 **Thompson NFA 模拟**。
- 再决定支持边界：是否支持捕获组、懒惰量词、反向引用、lookaround。
- 最后让测试驱动语法扩展，而不是一开始就追求“兼容 PCRE”。

## 核心原理

🧠 正则引擎的核心不是“写很多 if”，而是把模式转换成可执行结构。

### 1. 词法与语法解析

正则本身是一门小语言。以 `a(b|c)*d` 为例：

- `a`、`b`、`c`、`d` 是字面量
- `()` 用于分组
- `|` 表示分支
- `*` 表示前一子表达式重复零次或多次
- 相邻元素天然表示连接

解析时常见难点不是 token 化，而是**运算符优先级**：

1. 量词 `* + ?` 绑定最紧
2. 连接次之
3. 分支 `|` 最弱

因此 `ab|cd*` 应被理解为 `(ab) | (c(d*))`，不是别的组合。你需要显式处理这种优先级，否则构造出的自动机会错。

### 2. 从 AST 到自动机

最经典路线是 **Thompson Construction**：

- 字面量 `a` 生成一条从状态 `s` 到 `t` 的 `a` 边
- 连接 `XY` 把 `X` 的终态接到 `Y` 的初态
- 分支 `X|Y` 用 epsilon 边从新起点分别跳到 `X/Y`
- 星号 `X*` 用 epsilon 边构造“进入、重复、退出”环

这里的关键是 **epsilon 转移**：不消费输入字符也能切换状态。它让“结构组合”变得简单，是 NFA 构造的核心技巧。

### 3. 执行：不是走一条路，而是同时维护一组可能状态

NFA 执行时，同一个输入位置上可能存在多个可达状态。对每个输入字符：

1. 先求当前状态集合的 epsilon 闭包
2. 用输入字符推进所有可匹配边
3. 得到下一批状态，再继续求闭包
4. 输入结束后，只要状态集合中含有接受态，即匹配成功

这与“回溯一条路径失败后再试另一条”不同。Thompson NFA 的优势是：它天然避免某些灾难性回溯。

### 4. 回溯引擎 vs NFA 引擎

| 维度 | 回溯型 | Thompson NFA |
|---|---|---|
| 实现直觉 | 更贴近递归下降 | 更贴近编译器/自动机 |
| 特性扩展 | 容易支持反向引用、lookaround | 对这类高级语义不自然 |
| 性能风险 | 可能灾难性回溯 | 通常更稳定 |
| 学习价值 | 理解“语义尝试” | 理解“结构编译” |

例如 `(a+)+b` 在输入 `aaaaaaac` 上，回溯型实现若不控制策略，可能指数爆炸；NFA 模拟通常不会因为“路径尝试树”而退化得那么离谱。

### 5. 捕获组不是“匹配成功顺手记一下”

一旦支持 `()` 捕获，执行层就不只是判断真假，而要记录：

- 组开始位置
- 组结束位置
- 分支竞争时哪个捕获结果生效

这意味着执行状态里要携带**额外上下文**。如果走 NFA 路线，捕获会让状态从“纯状态编号集合”升级为“状态 + 捕获快照”的组合，复杂度会明显上升。

### 6. 锚点与字符类体现的是“匹配语义”

- `^` 不是字符，它约束的是“当前匹配位置必须在文本起点”
- `$` 约束的是“当前匹配位置必须在文本终点”
- `[a-z]` 不是多个分支的简单语法糖，它是“一个字符集合判断”
- `.` 也不是任意字节这么简单，往往涉及是否跨行、是否匹配换行

也就是说，引擎不仅要处理“消费字符”，还要处理“零宽条件判断”。

## 适用场景

🛰️ 正则引擎适合处理“文本形状稳定、语义层次较浅”的任务：

- 日志筛选：提取时间戳、级别、错误码、请求 ID
- 词法预处理：把源码切成 token 的早期阶段
- 配置校验：邮箱、版本号、URL 片段、日期格式
- 批量替换：按模式重写文本
- 数据清洗：从半结构化文本中快速抽取字段

判断是否该用正则的一个实用标准是：**你要识别的是“局部模式”，还是“递归结构”**。前者通常适合，后者通常不适合。

## 不适用边界

🚫 正则引擎并不适合所有文本问题，尤其不适合以下几类：

- **递归嵌套结构**：例如任意层级括号、HTML/JSON/SQL 完整语法。它们更适合 CFG/解析器，而不是普通正则。
- **强语义约束**：例如“变量先声明后使用”“左右引用一致”等，需要上下文语义，不是模式匹配。
- **超大规模复杂模式**：当规则集合极大、动态拼接频繁时，可维护性和调试成本会迅速恶化。
- **性能敏感且来源不可信的模式输入**：回溯型正则在恶意输入下可能触发 ReDoS。

一个常见误区是：正则能匹配很多东西，所以想拿它“顺便”解析完整语言。结果往往是模式越来越长，边界越来越脆，最后既难读也难证正确。

## 为什么它重要

⚡ Regex Engine 是理解“语言实现最小闭环”的优秀入口，因为它把多门基础能力压缩到了一个小而完整的系统里：

- 你会真正接触**语法设计**：一个符号的优先级与结合性会直接改变语义。
- 你会真正接触**编译思想**：输入的不是程序源码，但你仍然在做“解析 -> 编译 -> 执行”。
- 你会真正接触**自动机理论落地**：NFA/DFA 不再是课本图，而是运行中的数据结构。
- 你会真正接触**性能与安全**：同样功能，不同实现策略的复杂度差异巨大。

更重要的是，它训练的是一种工程判断力：面对“看似只是字符串处理”的需求，你会学会区分哪些问题是**语法问题**，哪些是**状态机问题**，哪些已经升级成**解析器问题**。

## 建议延伸

🌌 如果你已经完成一个最小可用版本，建议按下面顺序扩展，而不是一口气补全所有高级特性：

1. **字符类与转义**：`[0-9]`、`\d`、`\w`、`\s`，把模式语言从玩具提升到实用。
2. **编译缓存**：模式编译一次，多次复用，理解“解释执行”和“预编译”的区别。
3. **DFA 子集构造**：把 NFA 状态集合压成 DFA 状态，观察时间换空间的典型工程权衡。
4. **捕获组实现**：理解“识别语言”和“提取结构”之间的复杂度跃迁。
5. **错误报告**：当模式非法时，准确指出位置与原因，这会倒逼你完善 parser 设计。
6. **性能对比实验**：对比回溯实现与 NFA 模拟在特定模式上的耗时，建立复杂度直觉。

建议带着这几个问题继续学：

- 为什么有些正则特性能让引擎很强大，但也让自动机实现变复杂？
- 为什么工业引擎常常不是“纯 DFA”也不是“纯回溯”，而是混合策略？
- 为什么很多安全问题最终会落到“模式设计不当 + 引擎策略不当”这个组合上？

> `Regex Engine` 值得学的地方，不在于会写几个花哨模式，而在于你能看见：  
> **文本匹配背后，其实是一次受限但完整的语言执行过程。**
